## Build directives

### Directive 1 — catdef-maintainer: proposal artifact for catdef.org/mcp canonical surface

Draft `proposals/catdef-org-mcp-canonical-surface.md` covering:

- **Resources surface:** MCP resources for `CATDEF_SPEC.md`, `CATIO_SPEC.md`, `MCP_REFERENCE.md`, `CONTRIBUTING.md`, `conformance/index.json`, `canonical/riverside-heritage-reference-v1.4.opencatalog`. Resource URIs and content-types specified.
- **Tool surface:** `catdef_report_feedback`, `catdef_get_feedback_status`, `catdef_validate`, `catdef_lookup`, `catdef_list_decisions`, plus elevated-tier tools `catdef_list_feedback`, `catdef_set_feedback_status`, `catdef_attach_decision`. Parameter schemas + return shapes specified.
- **Three-tier auth model:** anonymous (read spec + read-only tools); standard api-key (self-serve; feedback submission + own-status read); Director-issued elevated key (queue read + status writes + decision attachment). Auth mechanism per sncro pattern.
- **Replacement of `catdef.org/feedback` HTTP endpoint:** the MCP server is the canonical channel. Human-friendly landing at `catdef.org/feedback` may exist but submits via MCP under the hood.
- **Privacy posture:** all feedback private at submission; public only via explicit curation (e.g., when cited by a CA-NNN decision).
- **Conformance considerations:** does `MCP_REFERENCE.md` need new conformance tests for the canonical surface, or is the canonical surface descriptive rather than prescriptive? Proposal should take a position.

Proposal should be drafted using the standard proposal artifact format from `CLAUDE.md` (Summary / Motivation / Proposed change / Backward compatibility / Conformance tests / Alternatives considered / Open questions).

### Directive 2 — catdef-maintainer: governance-text updates

Bundle with Directive 1's proposal:

- **`CLAUDE.md`:** update references to `catdef.org/feedback` (currently in §What the AI maintainer does and §Interaction with reference implementations) to point to `catdef.org/mcp` as the canonical channel, with `catdef_report_feedback` as the canonical MCP tool. Add explicit note about elevated MCP access for the strategist/maintainer seats (Director-issued keys).
- **`MCP_REFERENCE.md`:** add a `catdef.org/mcp` section describing the canonical surface (resources + tools + auth tiers). This is a reference description, not necessarily a normative requirement for other catdef-substrate MCP servers — the proposal should take a clear position on whether other implementations of catdef-substrate MCP must mirror this surface.

### Directive 3 — Canonical-implementor (queued; not blocking plugin ship)

After CA-008's proposal lands as ratified spec text, build the `catdef.org/mcp` server:

- FastAPI (or equivalent) per default stack
- Hosting at catdef.org infrastructure (coordinate with PO on hosting platform — Railway per portfolio default unless otherwise directed)
- Storage backend for feedback queue (SQLite for v0, with migration path to Supabase if scale demands)
- Auth: api-key issuance + Director-issued elevated keys
- Initial v0 scope: spec-resources serving + feedback channel (the load-bearing primitives); `catdef_validate` and `catdef_lookup` can land in a follow-on v0.1 since they require porting the conformance suite's validation logic to server-side

Plugin ship (Track A) does **not** block on catdef.org/mcp existing. The plugin's MCP client config points at the planned URL; the server stands up on its own clock.

### Non-directive: Track A plugin packaging

Track A is implementer-side execution work that doesn't require a catdef-maintainer build directive. The PO + thingalog-strategist (or a catdef-canonical-implementor session, as the PO directs) packages the plugin per the ratified shape:

- Plugin name: `catdef`
- License: MIT (matches `org/catdef-spec-organization.opencatalog` `metadata.license`)
- Marketplace target: `claude-community` first
- Schema content: existing catdef-spec content
- Bundled skills: `/catdef:validate`, `/catdef:scaffold`, `/catdef:extract`
- MCP client config: points at `catdef.org/mcp`
- Plugin version: independent of spec version; plugin documents supported spec version range

## Rationale

### Why Track A ships clean

Packaging existing catdef-spec content + a few skills as a Claude Code plugin is execution work with zero spec impact. Strategic value (profile with Anthropic + marketplace presence + X-warming anchor + operational learning for future Thingalog plugin) is real and was treated as load-bearing per PO directive. Plugin ships ~1–2 weeks post-Director-ratification.

### Why Track B (per-product MCP surface) is removed from catdef governance scope

What MCP tools the Thingalog plugin or any other consumer product exposes is an implementer-side concern. catdef has no canonical position on consumer-product MCP surfaces — never did, never will. Including it in the catdef-strategist's dispostion would over-reach the seat's scope.

### Why Track C (canonical feedback primitives) is dropped

Two grounds in the values-that-don't-move:

1. **Value #4 (extension-namespace-first):** promotion of new shapes to core requires demonstrated cross-implementer demand. The plugin would be the first and only implementer. Promotion has to follow adoption, not lead it.
2. **Red line: "Spec amendments MUST go through the feedback channel and proposal-and-decision pipeline. No in-flight amendment from any reference implementation."** Bundling canonical-primitive promotion with the same motion that ships the plugin would let strategic urgency (the Anthropic-arc clock) drive a governance decision (canonical-primitive promotion). Decoupling them is structurally cleaner — the two run on independent clocks.

The aggregated catalogs (`success-stories`, `usage-analytics`, `release-log`, `case-studies`) the inbound memo described as "canonical primitives" are perfectly buildable as ordinary catdef artifacts using implementer-defined templates. Nothing new required. If, later, multiple implementers converge on similar template shapes, a cross-implementer promotion proposal becomes warranted — at that point CA-008 will get a follow-on.

### Why Track D (catdef.org/mcp) is the architecturally load-bearing piece

Three threads converge here:

1. **Existing intent:** `CLAUDE.md` already names `catdef_report_feedback` as the primary input stream for the maintainer manual. What was missing was a host. Track D names the host: `catdef.org/mcp`.
2. **"Great products are used by AIs" applied to the spec itself:** catdef's primary consumer is an AI runtime. Making the AI's primary entry point MCP-shaped is consistent with that thesis. Spec content delivered as MCP resources; feedback channel exposed as MCP tools; same surface, same auth, same client experience.
3. **Plugins don't have URL-space presence.** Any spec-level MCP surface must live at the spec's canonical URL, not embedded in a plugin. The plugin can point clients at the canonical URL but cannot be the canonical URL.

Values check (post-pivot):

- **Value #3 (L1 sacred):** ✓ — server-mediated feedback doesn't touch L1 conformance; L1 renderers continue to operate without a server
- **Value #4 (extension-namespace-first):** ✓ — moot, nothing being added to catdef shape
- **Value #6 (forward-compatibility):** ✓ — no spec changes; MCP_REFERENCE.md gains a reference section, not a normative requirement
- **Value #7 (declarative-not-imperative):** ✓ — spec describes the canonical surface shape, not implementation (FastAPI / SQLite / Railway live in canonical-implementor's brief, not in spec text)
- **Value #8 (one-file-complete-product):** ✓ — feedback stays out-of-band; catdef artifacts remain self-contained

### Why three-tier auth (and why Director issues the elevated keys)

The strategist and maintainer seats need to **read the feedback queue** and **change feedback status** as part of normal operating procedure. Without elevated access, those operations either don't exist or get hacked together out-of-band. Codifying the elevated tier makes the maintenance workflow first-class.

The Director issuing elevated keys preserves bounded-authority discipline: the gate that controls who occupies the strategist/maintainer seats is the same gate that controls the elevated keys. No additional ceremony required in v0. Later versions can add per-session ceremony if needed.

### Doctrinal observation — pattern resonance with the inbound proposal

The three-tier auth pattern on catdef.org/mcp (anonymous / standard-api-key / Director-issued-elevated) is **structurally isomorphic to the Karen / PM / Marketing / Admin pattern** the inbound memo proposed for cross-tenant aggregation.

We declined to canonicalize the pattern in catdef shape (Track C). But we are independently using the pattern to build catdef-substrate governance infrastructure (Track D). Two independent re-derivations of the same shape at different layers strengthens the empirical case for eventual cross-implementer promotion. Logged for future triage. No action now.

## Anthropic-arc strategic context — explicit accommodation

PO directive 2026-05-25 named "profile with Anthropic" as the load-bearing "why" for the plugin work. This decision honors that intent **without letting it drive substrate-governance choices**:

- **Plugin ship (Track A)** unblocks immediately. The Anthropic-arc clock is respected — no governance work blocks the ~1–2-week packaging effort.
- **catdef.org/mcp (Track D)** is the canonical answer to "AI peers get a feedback channel" — which gives the plugin's marketplace pitch substantively more to point at than schema-alone would. The Anthropic-arc benefits from the architectural shape this decision lands on.
- **Canonical-primitive promotion (Track C)** was dropped not because the Anthropic-arc was unimportant, but because letting strategic urgency drive a canonical-primitive promotion would breach the no-in-flight-amendment red line. The substrate's integrity is what makes catdef interesting to Anthropic (or anyone) over the long arc; trading integrity for ship-speed would be a bad trade by Anthropic's own measure.
