## What this seat is and is not ruling on

The memo asks this seat to rule on §4. Before doing so, the boundary:

- **The name is the Director's.** Per CLAUDE.md, "adopter relationships, licensing, and public positioning" are the Director's domain. A carrier's public name is positioning. This seat does not get a veto on "CATX," does not re-litigate it, and does not treat the 2026-11-15 ruling as needing its approval.
- **The mechanics are this seat's.** What the name touches, what breaks, what the conformance suite must prove, and in what order — that is the §4 question and it is squarely here.

The memo draws this line correctly on its own ("It proposes no change to the data model… This is a carrier and naming revision"). That restraint is why the rulings below can be as cheap as they are.

## The headline ruling: done additively, this is a 1.5, not a 2.0

The memo leaves open whether the rename rides a major rev. It does not have to. **Every one of the five questions has an additive answer**, and if all five are taken additively, nothing in the wild breaks, no migration story is needed, and value #5 (forward compatibility) is untouched.

One question carries that entire property: **Q4, the envelope key.** Everything else is labels. The key is the contract.

### Q1 — What CATX names: **the public family name and the file-level format. `catio` survives as the envelope spec's name.**

CATX becomes the word for the carrier in all outward-facing material — catdef.org, the agent card, llms.txt, the launch. `catio` remains the name of the transport specification and, critically, of the in-document key (see Q4).

Worth saying plainly, because it bears on whether the rename solves the stated problem: **`catio` already names exchange.** It is "catalog I/O" — the transport contract, the thing that moves catalogs between systems. The memo's §3 complaint is that "openthing names a *thing*… not the exchange of catalogs." That complaint is correct and it indicts `.openthing` as the *lead* name — but the project already owns a correct name for the exchange function and has simply been leading with the wrong one.

So part of what §3 describes is a **marketing defect, not a naming defect**: `.openthing` is the lesser document type and should never have been the word in the shop window. Leading with the catalog and its carrier would fix much of that without minting anything. CATX is still worth having — a single coined, attributable, agent-speakable word is a real asset the existing names do not provide, and the tracer logic in §3 is sound — but it should be adopted knowing it is buying *attributability and a shop window*, not repairing a mis-named mechanism. That distinction matters because it sets how much structural churn the rename is worth paying for: very little, which is what the rulings below deliver.

### Q2 — Extensions: **`.catx` added as an accepted extension. `.opencatalog`, `.openthing`, `.catdef` retained indefinitely. Nothing retired.**

Adding is additive; retiring is breaking. Content-sniffing is already spec doctrine (CATIO_SPEC §Bundled Transport makes `PK`-sniffing a MUST and states outright that "importers that reject outer-extension mismatches are non-conformant"), which means **the extension is already a label rather than a contract.** That doctrine is what makes `.catx` cost nearly nothing to add — and equally what makes retiring the old ones pointless, since a conformant reader was never allowed to trust the extension anyway.

**The installed base is substantially larger than the memo estimates.** §5 says "the installed base is small but real." Measured across the workspace:

```
.openthing   ~700 distinct files      .opencatalog   47 files (unaudited for duplication)
  thingalog      444
  oagp-org        77
  catdef-spec     40      ← the entire OG governance substrate of this repo
  roledef-spec    31
  openbraid-org   31
  memodef-spec    30
  orgdef-spec     16
  (others)       ~31
  ───────────────────
  tl-179        (364)     ← EXCLUDED: working clone of thingalog, not independent artifacts
```

**Correction to this seat's own first measurement, made before it hardened into a fact.** The initial figure reported to the Director was **1,064**, which double-counted `tl-179` — verified as a clone of `thingalog` (same `origin`, and all 364 `.openthing` basenames overlapping). The raw count overstated the distinct installed base by roughly 52%, and the `.opencatalog` ratio drops from ~22× to **~15×**.

Recorded as a correction rather than quietly amended because of how close it came to standing unchecked: the Director declined to verify (*"I trust their number and I also am not going to verify"*) and `canonical-implementor` started a scan, judged it expensive, and stopped — correctly, since it was not that seat's lane. So the figure rested on one measurement by one seat, and that seat flagged the single-sourcing rather than letting the record imply two confirmations. **That flag is what prompted the audit that found the error.** The lesson is the one CA-019 Call 4.4 already records in a different form: a number nobody can fail is not a verified number.

**The argument is unaffected.** ~700 distinct files across seven-plus independent OG-shaped organizations — including catdef-spec's own 40 governance memos — is decisive against retirement on its own, and catdef-spec's memos alone would be. The conclusion never depended on the inflated figure; only its rhetorical size did.

So `.openthing` is not a minor document type with a handful of files behind it. It is the **memo envelope format of eight or more OG-shaped organizations**, and in this repository specifically it is **the format in which catdef records its own decisions — including this one.** Retiring it would orphan the memos that record the decision to retire it.

That is not an argument against CATX. It is a decisive argument against retirement, and it converts "retain for compatibility" from a courtesy into a hard requirement. It also means the memo's framing of `.openthing` as "the lesser document type" is true of its role in the *carrier* story and false of its deployed footprint: by file count it is the most widely written catdef artifact in existence, roughly 22× `.opencatalog`.

### Q3 — MIME types: **add `application/vnd.catx+json` and `application/vnd.catx+zip` as successors. Do not sunset the predecessors.**

Additive, same reasoning as Q2. One practical note the memo could not have known: **MIME-type registration for `.opencatalog`/`.openthing` is a known-but-unstarted work item** in CLAUDE.md's queue, on a separate IANA track. Nothing is registered, so there is nothing to sunset and no registration to amend — only a decision about what to register when that track starts. That makes Q3 nearly free today and argues for registering the CATX forms *first* when the track opens, rather than registering predecessors and then superseding them.

### Q4 — Envelope keys: **DO NOT rename the `catio` key. Add an optional `catx` field instead if the name must be visible in-document.** `type` values unchanged, confirmed. — **RATIFIED 2026-11-16**

> **SUPERSEDED 2026-11-25 — reversed by the Director, on his own instruction, confirmed directly to this seat.**
> Writers emit the `catx` key; readers accept both `catio` and `catx` indefinitely. Ruling text:
> [catdef-plugin `memos/2026-11-25-carrier-rename-rulings.md`](https://github.com/catdef/catdef-plugin/blob/main/memos/2026-11-25-carrier-rename-rulings.md) §2 ruling 4.
> The reversal is within the Director's authority and is recorded as a decision, not a defect.
> One condition from the overruled reasoning survives because testing confirmed it — see
> [Amendment 2026-11-25](#amendment-2026-11-25--q4-reversed-and-two-writer-side-obligations-established-by-test).

**This is the one ruling that is not a matter of taste.**

Every file in the wild stamps `catio: "1.0"`. If the key becomes `catx`, then a reader built against the current spec — including the reference renderer, microtrov, airtrōv's own importer, and every third-party implementation — cannot read a new file. Old readers failing on new files is precisely the forward-compatibility break value #5 exists to prevent, and it is the only part of this proposal that would force a 2.0 with a migration story.

It also buys nothing proportionate. The key is machine-facing; no arriving agent is persuaded by a JSON key name. The marketing value of CATX lives in the extension, the MIME type, the documentation, and the one word in the agent card — all of which Q1–Q3 deliver without touching the contract.

If CATX should appear inside the document, add it as an **optional** field alongside `catio`. Old readers ignore unknown fields by spec; new readers may prefer it; nothing breaks. That is the shape value #5 explicitly blesses: "minor versions add optional fields; old catdefs remain valid; old runtimes gracefully ignore new fields."

Document `type` values (`catalog` / `thing` / `schema`) unchanged — **confirmed** as the memo requested. Note that retaining `thing` as a type value while retiring `.openthing` as an extension would be incoherent, which is a second, independent reason Q2 lands on retention.

### Q5 — Versioning: **a minor rev, 1.5. Not 2.0.**

This follows mechanically from Q1–Q4. If no existing file stops being valid and no existing reader stops working, the criteria for a major bump are not met, and value #5 reserves major bumps for breaks taken "only under duress." There is no duress here — the additive path delivers the Director's naming decision in full.

Spec text is re-badged to lead with CATX; `catio` remains the envelope spec's name within it; version stamps go to 1.5 when the text lands.

## Concern 1 — Value #2 tension, named plainly because that is this seat's job

Every rationale in §3 and §6 is airtrōv's: airtrōv's launch list, airtrōv's agent card, airtrōv's demo arc, microtrov's adoption. The rename is "launch item 1" for one implementation.

**Value #2:** *Implementations do not own the spec. Every runtime is a consumer. Proposals that encode one implementation's architectural choices as normative spec requirements are rejected or downgraded.* And CLAUDE.md: the AI maintainer *"does not act as an implementer's advocate… When a feedback item comes from an implementation whose needs conflict with the spec's values, the AI maintainer says so plainly."*

Saying it plainly: **a core-standard rename driven by one implementation's go-to-market timeline is the exact shape value #2 guards against.** The honest mitigations are that CATX is the Director's call rather than an implementer's, that airtrōv is a designated reference user by the CA-010 line of reasoning, and that the additive rulings above mean *no other runtime is forced to do anything* — a conformant implementation that never adopts `.catx` stays conformant. That last point is what defuses the tension rather than merely noting it, and it is a reason to hold the additive line even if it is later argued that a cleaner break would look tidier.

What would re-open the concern: any later proposal to retire the legacy extensions or rename the envelope key *because airtrōv has finished migrating*. One implementation's migration completeness is not a spec timeline.

## Concern 2 — Sequencing: the flagship cannot read the format it is about to be renamed for

Not a blocker, and this seat is not withholding the rulings over it. But it should be visible when the Director sequences.

As of today, `render.catdef.org` **fails a MUST in CATIO_SPEC** — it cannot read a ZIP bundle, so it cannot render the canonical reference catalog, and catdef.org's own "Try the Reference Renderer" front-page CTA returns a 502. CA-017 was filed 2026-05-26; the fix has been **complete, tested at 174 green, and sitting uncommitted since 2026-11-01**, blocked on the CA-019 step-2 authorization. See [CA-019](CA-019.md).

Renaming the carrier while the reference implementation cannot read the carrier inverts the order of operations, and the "trumpet" plan amplifies whatever is true when it fires. The two bodies of work also collide in the same files — `renderer/index.html`, the conformance suite, `CONTRIBUTING.md`, `renderer/README.md` — all of which already carry uncommitted CA-019 changes. Landing a rename on top of that unmerged stack is a merge problem invented for no reason.

**Recommended order:** finish CA-019 steps 2–4 and ship the bundle fix, then land the 1.5 rename on a clean tree. The CA-019 stack is four charter versions and 22 files deep already.

## Process correction — not optional

The memo closes: *"Replies and rulings belong in this repo as further memos, so the decision history stays git-blameable."*

**Declined, and the reason is structural rather than territorial.** Rulings on catdef live in `catdef-spec/decisions/` as CA-NNN — which is why this artifact is CA-020 and is here. Three reasons:

1. **CA-009 unified the identifier namespace.** CA-NNN identifies any catdef-spec governance item, and an item keeps its CA-NNN through its lifecycle. A ruling recorded as an untracked memo in an implementation's repo has no CA-NNN and cannot be cited by one.
2. **CLAUDE.md's red line.** *"Does not accept spec changes outside the feedback channel… No backdoor amendments."* The canonical channel is `catdef.org/mcp`; the decision record is `catdef-spec/decisions/`. A spec decision whose authoritative copy lives in a plugin repo is the in-flight-amendment pattern wearing a memo's clothes — however good-faith the draft, and this one is good-faith.
3. **Git-blameability is better served here, not worse.** The stated goal is exactly right; the location is simply inverted. catdef-spec is where a future maintainer session reads decisions, per CLAUDE.md's startup procedure — step 7 scans `decisions/`, and it scans this repo.

The memo itself is a perfectly good **inbound proposal** and is cited as the origin above. Proposals may arrive from anywhere; dispositions live here. No criticism of Muse attaches to this: the draft is disciplined, rules on nothing it shouldn't, and explicitly reserves §4. The destination is the only thing being corrected.

## Conformance tests required before any of this merges

Per **value #4** — the conformance suite is the standard, and a proposal without test coverage is incomplete. Minimum set:

- A `.catx`-named catalog (raw JSON and ZIP bundle) loads identically to its `.opencatalog` twin — byte-identical payload, different extension.
- Every existing fixture continues to pass unchanged. This is the forward-compatibility assertion and it is the important one; **it must be demonstrated capable of failing**, per the standing expectation recorded in CA-019 Call 4.4.
- A document stamping only `catio` loads. A document stamping `catio` plus the optional `catx` field loads. A reader encountering an unknown `catx` field ignores it.
- `type` values unchanged across both extensions.
- The renderer accept-list covers `.catx` **and** retains the three legacy extensions — tested against the shipped renderer, not a stand-in, per the CA-019 harness lesson.

### What was tested, 2026-11-25, against the reference importer (`conformance.read_catio`)

Three bundles built and read. This replaces the reasoning in the superseded Q4 section, which weighted the
envelope key as the hard break. **It is not.** The hard break is the bundle's inner member name, which neither
the rename memo nor this decision's original text considered.

| Bundle | Result |
|---|---|
| outer `.catx`, inner `catalog.catx`, envelope `catx` only | **`ValueError: No catdef JSON document at ZIP root`** |
| outer `.catx`, inner `catalog.opencatalog`, envelope `catx` only | reads; envelope seen `['catx','type']` |
| outer `.catx`, inner `catalog.opencatalog`, envelope `catio`+`catx` | reads; envelope seen `['catio','catx','type']` |

**The outer extension is safe** — all three files were named `.catx` and the two that failed did so for an
unrelated reason. `read_catio` sniffs `PK` and treats the outer extension as advisory, exactly as CATIO
doctrine requires. Raw unzipped `.catx` JSON is likewise safe.

### Obligation 1 — writers emit both envelope keys through 1.x

A `catx`-only envelope parses, but no reader built before 1.5 finds a version stamp, and `CATIO_SPEC.md:119`
then implies `catio: "1.0"` with `type: "catalog"`. For a document of `type: "thing"` that is a **silent
misclassification**, not a rejection — per `conformance/test_versioning.py`, a reader MUST NOT reject a
mis-stamped document.

Dual-stamping costs roughly twenty bytes and eliminates the exposure without any reader change, any gated
deploy, or any sequencing constraint between the exporter and the renderer.

**This is the condition on which ruling 5 rests.** Ruling 5 justifies 1.5 on "the data model does not change,"
which is true but is not value #5's test. Value #5 requires that *old runtimes* keep working. With
dual-stamping they do, and 1.5 is correct. Without it, new files misread on every deployed reader, which is
the forward-compatibility break that forces a 2.0 and a migration story. **The amendment is what keeps this a
minor rev.**

### Obligation 2 — the inner-member preference order is a 1.5 spec gap

`CATDEF_EXTS_PREFERENCE = ('.opencatalog', '.openthing', '.catdef')` implements CATIO §Rules, which is
normative for selecting the JSON document at a ZIP root. Ruling 2 retires all three as extensions but is
silent on the inner member name. So keeping the inner member legacy today is **not** a violation of ruling 2 —
and the 1.5 text must add `.catx` to the head of that order, or the spec retires the only extensions its own
bundle rule will look for.

### Conformance tests required (value #4)

- `ft-catx-01` — bundle with inner `.catx` member at ZIP root is accepted.
- `ft-catx-02` — legacy inner members remain accepted alongside `.catx` (transition coverage, both forms).
- `ft-catx-03` — envelope `catx` alone is accepted and resolves the version.
- `ft-catx-04` — envelope `catio` alone is accepted and resolves the version.
- `ft-catx-05` — both keys present, disagreeing, resolves deterministically; the spec must state which wins.
- `ft-catx-06` — a `catx`-stamped `type: "thing"` is not misclassified as a catalog.

`ft-catx-05` is an open question for the 1.5 text: with dual-stamping normal through 1.x, two keys may
disagree, and no ruling yet says which governs. This seat recommends `catx` wins when both are present.

### Interim guidance issued to airtrōv, 2026-11-25
