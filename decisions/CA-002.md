**Disposition:** Accept with modifications
**Origin:** [canonical/AUTHORING_FEEDBACK.md CA-002](../canonical/AUTHORING_FEEDBACK.md)

**Decided:** 2026-04-18 by scott (strategist review)

## Build directive

catdef-maintainer to revise the proposal with the following changes before opening the PR to main:

1. **Change version stamp from patch to minor.**
    Current: `Target version: 1.3.1 (patch — clarifies writer obligation; reader behavior under forward-compat is already defined)`.
    Revise to: `Target version: 1.4 (minor — introduces new writer-MUST, reader-MAY, and reader-MUST-NOT behaviors around version stamping)`.
    Update the Summary and Backward Compatibility sections to reflect that this is a new normative rule, not a pure restatement. This also aligns with CA-001's 1.4 stamp; the two proposals are now coordinated as part of the v1.4 release bundle.

2. **Feature-version index: backfill v1.1 and v1.2 columns before opening the PR.**
    The proposal's Open Question 1 notes this requires "a day with `git log -p -- CATDEF_SPEC.md`." That reconstruction is now a precondition for merge, not a follow-on. Reasoning: the proposal's normative rule ("writers MUST stamp per the feature-version lookup") is unenforceable for features introduced in v1.1/v1.2 without a complete index.
    Deliverable: a filled-in `### Feature-Version Index` section with entries for v1.0, v1.1, v1.2, v1.3, and v1.4-proposed. Leave the index non-normative as drafted (authoritative definition remains the spec text at a tagged version), but require completeness for the writer-obligation rule to be enforceable.
    Remove Open Question 1 from the proposal once backfilled.

3. **Resolve the prerelease-stamp question in-proposal (Open Question 3).**
    Add explicit normative text creating a tight, named exception for the canonical and reference documentation:

    > **Canonical and reference-document exception.** During active development of an unreleased minor version, the canonical reference file(s) and normative reference documentation MAY declare the target version stamp (e.g., `"catdef": "1.4"`) before that version is released. This exception applies only to the canonical and to documents explicitly identified as reference documentation by the catdef maintainers. All other writers MUST NOT emit unreleased-version stamps. On release of the target minor, the exception terminates for that version — the canonical and references become subject to the standard writer-obligation rule.

    This sanctions the canonical's current `"catdef": "1.4"` stamp explicitly. Remove Open Question 3 from the proposal once this text is added.

4. **No other substantive changes.** The core design is approved as-drafted:
    - Writer MUST declare at least the minimum version required for the feature set
    - Writer SHOULD declare exactly the minimum (over-stamping permitted but discouraged)
    - Reader behavior unchanged: graceful-ignore on unknown fields, MAY warn, MUST NOT reject on stamp mismatch
    - Asymmetric writer-strict / reader-lenient framing retained (Postel's Law; cite it explicitly if useful)
    - Conformance tests ft-version-01 through ft-version-04 retained as-drafted
    - Feature-version index home: inline in CATDEF_SPEC.md as an appendix (per the proposal's Requested Maintainer Actions bullet 3)

5. **Release-management constraint.** The revised PR may open and accumulate review, but merge-to-main is held until the full v1.4 bundle is coherent: CA-001, CA-002, CA-003 (once triaged), the i18n / `primaryLocale` work, and the MCP conformance work. Uncoordinated merges will produce a spec in which the stamping rule contradicts itself mid-version.

## Rationale

**Version stamp.** Consistency with CA-001 is the primary reason; the two decisions set the v1.4-era pattern for what rises to minor vs stays patch, and inconsistency here would undermine both. Secondary reason: the proposal really does introduce new normative obligations — a writer that correctly passed conformance at v1.3 can become non-conformant at v1.4 without changing any line of code, solely because the stamping rule is new. That's minor-level by any reasonable reading of value #5.

**Feature-version index backfill as precondition.** The normative rule depends on the index. Merging the rule without the index ships a standard whose conformance test can't be run against half of catdef's own feature surface. That's a quality bar the spec shouldn't cross. Requiring the backfill up front is a small additional cost (the proposal's own Open Question estimates it at a day) that yields a fully enforceable rule at release.

**Prerelease exception.** The canonical already stamps `"1.4"` pre-release. Under CA-002's strict reading, the canonical is its own first non-conformant artifact — a governance contradiction the moment CA-002 lands. Two ways out: (a) loosen the rule (rejected — loses discriminator value), or (b) name a tight, scoped exception (preferred — keeps the rule strict for the 99%, sanctions the narrow case that matters). The exception is bounded by who-can-use-it (canonical + named reference docs) and when (terminates on release), so it doesn't become a general loophole.

**v1.4 bundle.** CA-001 requires v1.4-capable importers. CA-002 governs when v1.4 features can be stamped. `primaryLocale` and the polymorphic-translation work are v1.4 features. The MCP conformance proposal targets v1.4. Releasing any subset of these without the others produces a spec where the stamping rule is unenforceable, or the feature exists with no corresponding stamp rule, or the canonical stops being valid mid-version. Bundled release is the only coherent path.
