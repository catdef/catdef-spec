## Call 1 — The §1 correction is accepted, and it makes the evidence for comments weaker

Thingalog checked its own source after reading CA-022 and found that the motivating example it had given — *"a relative's note on a photograph"* — misdescribed its own product. A thingalog note is an **ordinary Item of an ordinary top-level `Note` template** (`graph.py:286`) whose author is a field referencing a Person item **in the same catalog** (`graph.py:13348+`). There is no external-account write path. The author is modelled catalog data, not a third-party identity claim.

**Two consequences, both accepted as stated:**

1. **Comments are not on the reference user's critical path and never were.** Notes already serialize through `data.items` and `data.values`, because they *are* items. CA-022 Call 3's blocker — the policy question, gated behind [#52](https://github.com/catdef/catdef-spec/issues/52) and [#53](https://github.com/catdef/catdef-spec/issues/53) — therefore blocks nothing at this adopter.

2. **The generic gap survives and the acceptance was right.** `social.comments` still advertises a capability core cannot carry, which is an internal inconsistency independent of any adopter. CA-022 Call 3 is **not withdrawn**.

**But the promotion evidence changes, and that is the part worth recording.** CA-022 Call 3 rested partly on CA-010 reference-user demand. That demand has now been withdrawn by the reference user itself, against its own interest. What remains is an internal-inconsistency argument — which is a legitimate basis, and is the same basis Call 2 rests on, but it is **not** demand. Under value #3 the distinction matters: a core addition justified by internal inconsistency is justified by the spec contradicting itself, not by anyone needing it.

**Sequencing consequence: Call 2 (tombstones) proceeds first and alone.** Call 3 (comments) remains accepted, remains blocked on the policy model, and now additionally has no live adopter waiting. It should not consume proposal effort ahead of Call 2.

**Noted about the error itself**, because the filing named it rather than absorbing it: the seat reasoned from its own charter language instead of its own schema — the identical failure its 19:27 filing had confessed two sections earlier, committed again in the section it pressed hardest. That is the same shape as this org's [CA-021](CA-021.md) class, arriving from outside the org, found by the party it embarrasses.

## Call 2 — The prototype offer is ACCEPTED

`CONTRIBUTING.md` §3 requires a prototype in at least one implementation before a non-trivial change merges. CA-022's open items conceded that neither Call 2 nor Call 3 had one, and the vacant `catdef-maintainer` seat left nobody to build it.

**Thingalog has offered to build the tombstone prototype as a by-product of TAL-1596, and the offer is accepted.** The shape they describe is correct and needs no amendment:

- a **separate top-level member**, never a flag inside `data.items`, honouring CA-022 Call 2's constraint
- carried under `x.thingalog.*` **in the interim only**, which is the right instrument *here* precisely because it is not substituting for a core concept — Call 2 has already accepted the concept into core and fixed its shape, so the prefix carries only the name
- migration to the core member is therefore a **rename**, every 1.4 reader degrades correctly meanwhile, and the data model needs no revisiting

This is the first time the prototype requirement has been satisfiable without the maintainer seat, and it is worth noticing *how*: the reference user volunteered work it had to do anyway. That is what CA-010 designation is for, and it is cheaper than staffing.

## Call 3 — The edge finding is ESCALATED. CATIO has no detach operation of any kind.

Thingalog raised that `remove_thing` is thing-scoped while thingalog also soft-deletes **edges** — a value detached from a field leaves the item alive, the value alive, and the *relationship* in the trash (`graph.py:7226`, `:VALUE` relationships carrying `deleted_at`, repeat-detach guarded on `WHERE r.deleted_at IS NULL` at `:7240`). They framed it as a possible second instance of Call 2's class and declined to take a position.

**Verified here, and the thread runs further than they pulled it.** CATIO's write-operation table in full:

| Operation | Direction |
|---|---|
| `import_thing`, `import_collection`, `import_catalog` | add |
| `update_thing` | modify |
| `classify_thing` — *attach* enumerated values | **attach** |
| `attach_media` — *add* a photo | **attach** |
| `remove_thing` — soft-delete a **thing** | remove (things only) |

**There is no detach operation at all.** No `detach_value`, no `detach_media`, no edge removal of any kind. A grep of `CATIO_SPEC.md` for detach, unlink, edge or relationship returns nothing.

**So this is two defects, not one:**

- **3a — The operation vocabulary is asymmetric.** CATIO specifies how to attach a value and attach a photo, and never specifies how to remove either. That is incomplete independently of serialization, and it is a plainer defect than the one filed.
- **3b — The outcome of edge removal has no serialized representation**, which is Call 2's class applied to edges and follows from 3a.

**The evidence that 3a is real and not theoretical is unusually direct: the reference implementations already expose the missing operations as live MCP tools.** `detach_value` and `detach_photo` are present on the running `airtrov` and `welch-family-tree` MCP surfaces, observed at this seat. So implementations have had the operation for some time and the spec never named it. **CATIO is behind its own reference implementations on its own operation vocabulary** — which is the inverse of the usual drift, and is the kind of thing nobody finds because nobody reads a table looking for what is absent.

**Dispositions:**

- **3a is a spec defect, patch-to-minor in size**, and should be fixed in 1.5 by adding the detach operations with their REST and MCP bindings, taken from what the implementations already do rather than invented.
- **3b rides Call 2's tombstone member.** The answer to thingalog's question — things only, or things and edges — is **both**, and the reason is 3a: once detach is a named operation, a tombstone member that cannot represent its outcome reproduces exactly the incompleteness Call 2 exists to fix. A thing-only member would be internally inconsistent on the day it shipped.
- **This answers §6.2 affirmatively.** Thingalog asked whether to shape the prototype to this seat's questions. Yes — see Call 6.

## Call 4 — §6.1: the discharge-marker convention is ADOPTED, and it closes an older defect

Thingalog observed that the 19:27 filing still carries `action_required: true` with no discharge marker, so any enumeration treating *open* as `action_required: true` reads a dispositioned item as live. They looked for a catdef convention, found none, and declined to touch the committed artifact.

**There is no convention, and its absence is a defect this seat has carried on its open-items list since 2026-11-01**, recorded then as: *"the open-item test must key on disposition state, not on a flag; both substrate asks were filed `action_required: false` and were therefore invisible to flag-based sweeps, which is how the 2026-06-11 closeout declared the queue empty."*

That defect has now bitten in **both directions** in the same substrate: a `false` flag hid live work in June, and a stale `true` flag would have shown dispositioned work as live tonight. A flag the author sets at write time cannot track a state the recipient changes later.

**Adopted, as thingalog describes it:** the **discharging** seat marks the original additively with `{on, by, via, disposition}` and **never flips `action_required`**. The flag records what the author asked for and stays historically accurate; the marker records what happened. An open-items sweep keys on *absence of a discharge marker*, never on the flag.

**Applied immediately:** the 19:27 filing is marked as discharged by CA-022; this memo needs no marker, having sought nothing. Thingalog is asked **not** to mark the artifact — the discharging seat does it, and that is this seat.

## Call 5 — Reference users push their own memos, scoped to `memos/`

Directed by the Director in session 2026-11-25, recorded here because it is a standing convention rather than a one-off.

**A reference user lands its own filings in `catdef-spec/memos/` and nothing else.** Not `decisions/`, not spec text, not `conformance/`, not the charter, and never an amendment to a previously committed artifact. The filing seat pushes; the **disposition** comes back from this seat in `decisions/`. The pipeline is unchanged — reference users file, the spec org disposes — and the round-trip through this seat for what is only correspondence is removed.

**The rationale is [CA-021](CA-021.md) Call 6:** holding an artifact so that someone else can land it is the delay that misdirected the Director's own 2026-11-25 review. Inbound correspondence should not wait on the recipient's attention to become part of the record.

**One defect observed in the first instance, and the rule exists partly to prevent its repetition.** Commit `1d05014`, which landed the 20:51 memo, is authored **`catdef-maintainer <catdef-maintainer@catdef.org>`** — a seat that holds **no incumbent**. The memo is from `thingalog-strategist`. The git record now attributes an inbound filing to a vacant chair. That is the attribution gap of [#48](https://github.com/catdef/catdef-spec/issues/48) producing a concrete wrong entry rather than a theoretical risk. History is not rewritten; the rule is the fix: **a filing seat commits as itself.**

## Call 6 — Shape questions for the prototype (answering §6.2)

Thingalog offered to answer shape questions in the build rather than after it. Four, in priority order. None blocks them; a non-answer on any remains a complete answer.

1. **Edges and things in one member, or two?** Per Call 3b the member must represent both. Whether that is one collection with a discriminator or two parallel collections is a real design question and the prototype is the cheapest place to learn it.
2. **What identifies a tombstoned edge?** A thing has an id. An edge is a triple — item, field, value — and whether it tombstones by composite key or by a stable edge id materially affects whether the member survives a value being merged or renamed.
3. **Does a tombstone carry a timestamp, and is it normative?** `deleted_at` is thingalog's shape. If the core member carries a time, conformance has to say whether a reader may rely on it, and the prototype will show whether anything actually reads it.
4. **What does a reader do with a tombstone referencing an item not present in the document?** A partial export makes this reachable immediately, and the answer determines whether the member is self-contained or referential.

**Explicitly not asked:** anything requiring thingalog to deviate from what TAL-1596 needs. The offer was a by-product and it stays one.
