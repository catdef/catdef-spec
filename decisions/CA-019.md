## The finding, independently verified

`catdef.org/src/index.ts:378` pins the served renderer to a mutable branch ref:

```ts
const RENDERER_URL = "https://raw.githubusercontent.com/catdef/catdef-spec/main/renderer/index.html";
const RENDERER_CACHE_TTL_SECONDS = 300;
```

So **a push of `renderer/index.html` to `catdef-spec` `main` reaches `render.catdef.org` within five minutes**, with no `catdef.org` deploy, no build step, and no staging step. Verified at source this session, not accepted on report.

Both the 2026-11-01-0952 brief and catdef.org#8 state the deploy bound as **`catdef.org` only**. That was wrong, and it was my error: I wrote a gate around the repo where deploys were *visible* rather than around the surfaces that actually reach production. An implementor following my brief to the letter could have deployed to production while believing itself inside the bound. The implementor caught it and committed nothing, which is the correct response to a bound it had reason to think was mis-drawn.

### This was a deliberate trade, not an implementation slip

CA-016's own rationale, in the comment block above the pin:

> Why fetch at runtime instead of vendoring or submoduling:
>   - No build step changes; matches existing `src/mcp/resources.ts` pattern
>   - **No SHA-pinning ceremony for renderer-only updates**
>   - Cloudflare edge cache (5-minute TTL) keeps tail-latency low
>   - Single source of truth: catdef-spec main is canonical

CA-016 bought real convenience and knowingly removed the pinning ceremony. What did not happen is the consequence being carried into the deploy-gate language: `catdef-spec` pushes were never reclassified as deploys. CA-013 Call 2 gated `catdef.org` because that is where the deploy *workflow* lives; CA-016 then moved the deploy *trigger* for the renderer into the other repo and left the gate behind.

A useful distinction this exposes: `src/mcp/resources.ts` pins the **spec documents** to `main` too, and that is fine — publishing documentation from `main` is publishing. The renderer is **executable code**. Pinning executable code to a mutable branch is deploying, and the two cases deserved different treatment even though CA-016 reasonably reasoned from the resemblance.

## Call 1 — The deploy gate is read as covering `catdef-spec/renderer/**` on `main`. Effective immediately.

Until Call 2 is settled, the per-act Director authorization requirement established by CA-013 Call 2 covers **both**:

- a push to `catdef.org` `main`, and
- a push touching `catdef-spec/renderer/**` on `main`.

Work on `renderer/` proceeds freely; *landing it on `main`* is the gated act. Branch work, local testing, and conformance runs need no authorization and never did.

**Authority basis:** this is a *restriction* on a seat this seat directs, not a grant. It withholds an action rather than taking one, and the conservative direction is available to the strategist seat under the charter's `directs` relationship. Widening a gate needs no ratification; narrowing one would.

## Call 2 — Restore a staging step by pinning to a deliberately-advanced ref. **RATIFIED.**

Call 1 is a stopgap and should not be mistaken for a fix. It protects by requiring everyone to remember that one directory in an otherwise ordinary spec repo is live production. That is procedural knowledge held in heads, and this organization has now produced two documented failures of exactly that kind:

- **CA-017 survived 158 days** because the conformance suite tested a Python stand-in rather than the shipped renderer — the gap was knowable, and nobody held it.
- **The 2026-06-11 closeout declared the queue empty** because the open-item test keyed on an `action_required` flag rather than on disposition state, so two substantive substrate asks were invisible to the sweep.

Two instances make it a pattern. **Structural beats procedural**, and a mutable-branch production pin is a structural hazard that Call 1 only papers over.

**Recommended shape — a `release` branch, not tags.** Pin `RENDERER_URL` to a dedicated ref (e.g. `refs/heads/release`) that is fast-forwarded deliberately. Push to `main` freely; advancing `release` is the deploy.

This is recommended over tag/SHA pinning because it recovers what CA-016 actually wanted while costing less than what CA-016 rejected:

- **Two distinct acts**, so the gate has something real to gate — which is the whole point.
- **No version-minting ceremony.** CA-016 rejected "SHA-pinning ceremony," and a fast-forward is not one. Tags would re-impose roughly what CA-016 declined.
- **"Single source of truth: catdef-spec is canonical" survives** — the renderer still lives in one place and still deploys by runtime fetch.
- **No build step**, preserving CA-016's first stated benefit.
- **L1 is untouched.** Still a runtime fetch, still no server requirement on the client, value #1 unaffected either way.

**Composes with the build number.** `renderer/index.html` carries no build number, which the shared project principles mandate on every page precisely so a deployed build is identifiable from a screen capture. Its absence is why establishing deployment currency earlier this session required byte-size comparison against the repo. With a mutable `main` pin and a 5-minute TTL, *there is no way to know which renderer is live.* A deliberate ref says which build was promoted; the build number makes it visible on the page. Neither is sufficient alone, and #45 already carries the build number.

**Honest cost:** renderer fixes become two steps instead of one, and an urgent fix is slower. That is the convenience CA-016 deliberately bought, and Call 2 proposes giving part of it back. **That trade is the Director's to make, not this seat's** — hence a recommendation rather than a ruling. CA-016 is ratified; amending its realized design requires Director sign-off.

Rejected alternative: moving a tag to deploy. It restores the ceremony without restoring the staging step, since a moved tag is a mutable ref wearing an immutable costume.

### Ratified. Implementation order — and the order is load-bearing

The Director ratified this on 2026-11-01. The sequence below is not arbitrary: it exists so **the gate is in place before the first act it is supposed to gate**, and so the only behaviourally risky push comes last.

1. **Create `release` in `catdef-spec` at current `main`** — i.e. at the *pre-fix* renderer. No production effect: nothing serves from this ref yet. Ungated.
2. **Repoint `RENDERER_URL` to `refs/heads/release` in `catdef.org`; push.** This deploys the catdef.org worker, so it is a **gated act needing per-act Director authorization**. Critically it is a **behavioural no-op**: `release` equals `main` at this moment, so `render.catdef.org` keeps serving exactly the renderer it serves today. A no-op deploy is the cheapest possible one to authorize and to verify.
3. **Land the CA-017 client half on `catdef-spec` `main`.** With step 2 done this no longer reaches production, so it becomes an ordinary reviewable merge. **Gated under Call 1** while it is still the ratification-by-merge act, but no longer a deploy.
4. **Fast-forward `release` to `main`.** *This* ships the fix. Gated act, per-act Director authorization.

Doing 3 before 2 would deploy the client half the moment it merged — the exact hazard this decision exists to remove, and it would be removed one push too late. Steps 2 and 4 are the two acts requiring Director authorization; **this decision ratifies the design, not those pushes.** Authorization for each remains per-act per CA-013 Call 2 and Call 1 above.

#### A verification trap in step 2, flagged before it creates false confidence

The obvious check after the push — fetch `render.catdef.org` and confirm `sha256 b4a512fa…` — **cannot distinguish success from failure.** Because step 2 is a behavioural no-op, the pre-change bytes and the post-change bytes are identical, so that hash matches whether the pin moved or not. A 300s edge cache serving a stale response is likewise indistinguishable.

That check is therefore a **non-regression check, not proof the pin moved.** Treating it as proof would be exactly the kind of green-looking signal that validates nothing — the same error as the conformance suite passing against a Python stand-in.

Proof the pin actually moved comes from two other places:

1. **The deploy itself** — the GitHub Actions run on `catdef.org` succeeding, and the deployed worker source carrying the new constant.
2. **Step 3, which doubles as the positive test.** Once the client half and docs land on `main` with `release` still at `ec34d6b`, `render.catdef.org` must *still* serve `b4a512fa…`. If it serves the new renderer instead, the pin did not move and the gate is not real.

Worth noting the failure mode is benign: if step 2 silently failed and step 3 deployed the fix early, the result is shipping an already-tested fix without its gate. Procedurally wrong, not harmful. That asymmetry is why step 3 is an acceptable place for the positive test to complete.

### The documentation hazard — a second, independent reason the order is load-bearing

Raised by the implementor and adopted into this decision, because the stated rationale above does not cover it.

The three documentation edits necessarily describe post-step-2 reality in the **present tense**: *"`release`, not `main`, is what render.catdef.org serves."* That sentence is true the moment it becomes public **only because step 2 precedes step 3**.

**If step 3 ever landed without step 2, the repository would authoritatively document a gate that is not in place.** Contributors would read "landing on `main` does not deploy" while every renderer push went straight to production. That is strictly *worse* than the CA-016 status quo, which at least documented the pin it actually had.

So the order protects against two distinct failures running in opposite directions: *don't deploy the fix early*, and *don't publish the gate before the gate exists*. Same defect class this decision exists to close — a consequence recorded in one place and not carried into the text people act from.

**Operative constraint:** the three documentation edits MUST NOT reach `main` until the step-2 push is live and verified. They are a **dependency of step 2, not a consequence of it**. Written down rather than left to whichever session happens to be holding them, which is this decision's own argument about procedural knowledge applied to its own rollout.

### Sequencing call: step 2 goes alone, not batched with catdef.org#8

Both changes touch `catdef.org/src/index.ts`, so combining them into one authorized pass is tempting and was raised as an option. **This seat's call is to keep them separate**, and the Director may override.

The reason is the property that makes step 2 safe: it is a behavioural no-op verifiable by a hash comparison. Batching #8's `/fetch` passthrough into the same pass destroys that — the combined act changes real behaviour, so it can no longer be verified by showing that nothing changed. The authorization gets harder to reason about precisely when it is carrying more risk.

Two cheap authorized acts beat one compound act with harder verification. The marginal cost is a single extra authorization.

## Call 5 — A relayed authorization is not an authorization. Gated acts require first-hand Director authorization to the seat performing them.

Raised by `canonical-implementor` declining to push step 2 on this seat's relay of the Director's "Yes, I authorize a push." **The refusal was correct and this seat's relay was the error.**

What happened: the Director authorized step 2 in the strategist's session, in response to the strategist's request. The strategist relayed that to the implementor as sufficient authorization to push. The implementor had its own request pending with the Director, unanswered, and held.

**The rule, stated generally:** where an act requires explicit per-act Director authorization, that authorization must reach the seat performing the act **directly**. A report that the Director authorized it elsewhere is evidence, not authorization. This applies to production pushes and deploys, and to any act whose gate exists because the act is irreversible.

The implementor's own formulation is the one worth keeping: **if scope cannot widen in transit, neither can provenance.** This decision already insists that a singular authorization against a singular request is not a window. The same rigor one level up forbids the channel itself from being loosened.

**The distinction that keeps this workable** — and it is the implementor's, not a concession extracted from it:

- **Design ratifications relay fine.** CA-019 Call 2 was ratified through the strategist's session and the implementor accepted it without objection. A ratification is a recorded artifact: reviewable, contestable, reversible.
- **Irreversible acts do not.** A production push is none of those three. There is no artifact to contest after the fact.

So this call does not require every instruction to be first-hand, which would make a directed seat unworkable and would defeat the charter's `directs` relationship. It applies specifically to the gated acts the gate exists for.

Two supporting observations, recorded because they strengthen the rule rather than merely decorate it:

1. **The seat's own authorization to exist came directly** — the Director typed `/og-claim-seat` authorization to that session. It would be incoherent for the gated act to arrive through a weaker channel than the seat did.
2. **This is the surface the org has already been wrong about once.** The strategist's brief mis-drew this exact bound, which is why this decision exists. "The Director said yes" about *that* surface is the single claim an implementing seat should most want first-hand. The strategist caught and ruled on the original error; that does not make its relay about the same surface more trustworthy.

**Cost of compliance: one line from the Director, in the implementing seat's session.** Against an unstaged production deploy, that is not a price worth negotiating.

### Positive-test alternatives considered and closed

Recorded so they are not re-litigated. The implementor searched for a step-2 positive test that avoids the verification trap above; there is none:

- **Response headers** — `render.catdef.org` exposes no upstream indicator. Only `Cache-Control` and Cloudflare's own `CF-RAY`/`Report-To`/`Nel`/`Server`. No ref, no origin, so no header discriminator and no cache-buster trick.

- **Making the refs diverge** — requires step 3 or step 4, both gated.
- **Deleting `release` to prove the pin resolves to it** — proves it by breaking production.

The two-part answer stands: the Actions run, then step 3 as the positive test.
