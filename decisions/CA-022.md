# CA-022 Decision — CATX as a storage tier: the fork DISSOLVES into two questions with different answers; tombstones accepted as a defect, comments blocked on a policy question, canonicalization split

**Disposition:** The §4 fork is not one question. **CATIO is transport and should say so explicitly in 1.5. The catdef *document* is already a storage artifact by values #1 and #7**, so §3.1 and §3.2 need no fork answer at all. §3.2 (tombstones) is accepted as an **internal-incompleteness defect** — a stronger basis than demand — with one forward-compatibility design constraint the memo did not state. §3.1 (comments) is accepted as a core gap but is **blocked on a policy-model question**, not on the fork. §3.3 splits: the round-trip conformance test is accepted now and is the highest-value, cheapest item in the memo; the canonicalization MUST is deferred. §3.4 accepted as filed, against promotion. §6's declared deviation is **conformant**, and the spec should say so for free.

**Ratification state: RATIFIED by the Director 2026-11-25.** Call 1 was put as a scope question about what catdef is *for*, which CLAUDE.md reserves to the Director. **The Director ruled: storage.** The catdef document is a storage artifact; CATIO remains transport and says so in 1.5. All other calls are ratified as drafted, with one consequence the ruling creates that the drafting did not anticipate — see the Amendment at the end.

## 0. Citation audit — the memo's spec claims were verified, not accepted on report

Every line reference in the memo was checked at this seat before any of it was endorsed. All hold:

| Claim | Verified |
|---|---|
| `comments` exists only as a capability | `CATDEF_SPEC.md:267` (`features[]`), `:1564`, `:1761` (`social`), `:1792` (tier text). **No payload member anywhere.** |
| `remove_thing` is spec-defined | `CATIO_SPEC.md:151` — *"Soft-delete a thing (trash)"* → `DELETE /api/items/{id}` / `trash_item` |
| Preservation rules are per-field only | `CATDEF_SPEC.md:784` (URL object form), `:1447` (`x.*`) — both narrow, as claimed |
| Principle 3 is import-side | `CATIO_SPEC.md:15` — *"Importing the same catio document twice produces the same result."* |
| No round-trip test exists | Confirmed. `ft-catio-04` ("identical content, identical state") compares two **reads** and never writes. There is no export-fidelity test. |
| 25 fixtures available as a corpus | Confirmed, `conformance/fixtures/` |

**The memo's analytical core is correct and is adopted:** idempotent import is not lossless export. Principle 3 constrains the store after repeated application of the same input; it says nothing about what an exporter emits. An exporter can omit a field on every pass and the second import of the lossy export is just as idempotent as the first. **Principle 3 can hold while data is destroyed.** That reasoning gap is real, and it matters because Principle 3 is exactly what one would point at when asked whether round-tripping is already covered.

**One piece of filing discipline worth recording rather than passing over.** The memo opens by withdrawing advice its own seat gave the Director earlier the same day (that `.catx` might be redundant with `.opencatalog`), and names the reasoning error — reasoning about a design instead of reading the shipped artifact — as the same error that put a false statement in thingalog's own `CLAUDE.md`. It also files §3.4 with a recommendation **against** its own ask. A reference user that corrects itself and argues against its own interest is supplying better evidence than one that does not, and that bears on how much weight CA-010 designation should carry in future.

## Call 1 — The fork dissolves. It is two questions, and they have different answers.

The memo asks one question: *does CATX want to cover storage-tier use, or scope itself explicitly to transport?* Both branches it offers are coherent. **Neither is necessary, because the question conflates two specs.**

**CATIO is transport.** It self-describes that way, correctly — *"catio does not define what a thing is … catio defines how they travel."* It should **say so explicitly in 1.5**, exactly as the memo recommends, so the next adopter does not assume a warranty that is not offered.

**The catdef document is already a storage artifact, and the values say so.** §3.1 and §3.2 are not CATIO concerns at all — they are members of the `data` block of a `type: "catalog"` document, which is `CATDEF_SPEC`'s domain. `CATDEF_SPEC` has never claimed transport-only, and two values that do not move already settle it the other way:

- **Value #7 — "One file, complete product."** *"A catdef contains everything needed to go from zero to running application."* A courier does not care whether the package is complete. Completeness is a store's property, and the spec has asserted it from the beginning.
- **Value #1 — L1 is sacred.** L1 is a browser-only, no-server renderer reading a file. **At L1 the file *is* the store — there is no other one.** The spec's most fiercely protected tier is, definitionally, a storage-tier use. A format cannot hold L1 sacred and simultaneously disclaim storage.

So the honest statement is not *"should catdef take on storage-tier use"* but *"catdef has always been a storage format at L1, and the serialized document is missing things a store must carry."* That reframing is what makes §3.1 and §3.2 ordinary gap work rather than scope expansion.

**Consequence for thingalog, which is materially better than either branch offered:** no profile is needed for comments or tombstones. A profile would be needed only for §3.3's canonicalization, and only if that is adopted as a universal MUST — which Call 4 recommends against. The memo's fallback assumption (*if unanswered, proceed as transport-only and build a documented profile*) is therefore more expensive than necessary, and this disposition exists partly to spare that cost.

**This is a scope question about what catdef is for, which CLAUDE.md reserves to the Director.** Recommended, not ruled. If the Director prefers the memo's cleaner branch — CATIO transport-only *and* the document scoped to transport too — then §3.1 and §3.2 become profile work and this call is the thing to reject.

## Call 2 — §3.2 tombstones: ACCEPT. It is a defect, not a gap, and it carries one design constraint the memo did not state.

**The basis is stronger than the memo claimed for itself.** The memo offers §3.2 under cross-implementer demand, which it honestly concedes is one reference user. It does not need that basis. `CATIO_SPEC.md:151` defines `remove_thing` as a soft delete; nothing in the serialized document represents its outcome. **A format that specifies an operation but cannot serialize that operation's result is internally incomplete**, and internal inconsistency is a defect this seat flags on sight under its own triage heuristics — no demand required. Two conformant runtimes would disagree about whether a trashed item exists, which is precisely the interoperability ambiguity `CONTRIBUTING.md` lists under what SHOULD be proposed.

It is also aligned with the shared project principle mandating soft delete over hard delete across all projects in this family.

### The constraint: a tombstone MUST be a separate member, never a flag on an entry in `data.items`

The memo says an L1 reader ignores tombstones and renders live items only, *"which is the correct degraded behaviour."* That is true **only for one of the two obvious shapes**, and the other shape is actively dangerous:

| Shape | What a 1.4 reader does |
|---|---|
| `data.tombstones: [...]` — separate member | Ignores the unknown member wholesale. Renders live items only. **Correct degradation.** |
| `deleted_at` on an item inside `data.items` | Ignores the unknown *key*, keeps the item. **Renders deleted items as live — it resurrects the trash.** |

So the forward-compatibility story depends entirely on the shape, and the second shape silently un-deletes data on every old reader. **This is the same hazard as today's CATX finding**, in a different place: the danger is never what the new reader does, it is what the *old* reader does with new data, and the safe shape is always the one where the new thing is invisible rather than misread.

Specify tombstones as a separate member. Any proposal that puts a deletion marker inside `data.items` should be rejected on this ground alone.

## Call 3 — §3.1 comments: ACCEPT as a core gap, but it is blocked on a policy question, not on the fork

**Value #3 does not redirect this.** The extension-namespace test asks whether the thing can be expressed as `x.<domain>.<identifier>`. Mechanically it can; but the spec **already names `comments` in core** as a declarable capability, so an extension would fragment a core concept into vendor space and make a thing the spec advertises invisible to every runtime that did not invent the same extension. The memo's reasoning is right and is adopted: this is a missing payload for a concept core already has, not a vendor addition.

**But there is a question underneath it that the memo did not reach, and it is load-bearing.**

A comment payload would be **the first core content a catdef carries that was authored by someone other than the catalog author.** Every policy in the registry, and the whole trust contract value #9 protects, assumes a single author declaring intent over their own content. A contributed comment breaks that assumption:

- Who declares `.machine-translate: "Never"` over a contributed comment — the catalog author, or the commenter?
- The memo's own motivating example is *a relative's note on a photograph*. That is exactly the content where the answer matters most, and exactly the content where getting it wrong is least forgivable.
- A comment also carries a third party's name alongside their words, so attribution and consent travel with it whether or not the spec says so.

**§3.1 is therefore accepted as a gap and blocked on the policy model, not on §4's fork.** Drafting that question is this seat's work, not thingalog's and not the maintainer's, and it should land before any comment-payload spec text is written. Specifying the payload first and retrofitting policy later would bake in the single-author assumption at exactly the point it stops being true.

Recorded for the strategic record: this is the second time this month that the policy vocabulary has turned out to be the load-bearing part of an apparently unrelated feature.

## Call 4 — §3.3 splits, and the valuable part is nearly free

The memo bundles two properties that are separable, and the separation is where the whole economics of this item lives:

- **Losslessness** — no data destroyed on `document → store → document`. Verifiable by **semantic deep-compare**: parse both, compare structures. Needs no spec change.
- **Canonicalization** — byte-identical output for semantically identical input. **Strictly stronger.** Makes the test a byte diff, and tightens every writer.

**The memo's one overstatement is here.** It argues that *"without canonicalization, 'lossless' is unverifiable: any diff is ambiguous between data loss and serializer noise, so there is no test that can fail honestly."* That holds for a *byte* diff and not for a semantic one. A structural comparison verifies losslessness without any canonicalization at all; it is merely more work to write. Canonicalization is a convenience that makes the check cheap, not a precondition that makes it possible.

### 4a — Round-trip losslessness conformance test: ACCEPT NOW

Drive the existing 25 fixtures through `read → write → semantic-compare`. One test, no spec text, no compatibility story, and `CONTRIBUTING.md` lists conformance-test additions as a legitimate proposal class in their own right (value #4 — the suite is the standard). It would answer **today** whether the format round-trips at all, and this seat expects §3.1 and §3.2 to surface as its first failures, which is the useful outcome rather than an embarrassing one.

**This is the highest-value and cheapest item in the memo**, and it is the only one that needs nothing from the Director beyond a nod. Queued to the implementing seat behind `catdef.org#8`.

### 4b — Canonical byte-identical serialization MUST: DEFER

The tightening hazard the memo raises against itself in §5 is real and correctly characterised. A canonicalization MUST makes a writer that is conformant today — emitting valid but non-canonical JSON — non-conformant. That is not the additive shape value #5 blesses.

The memo's own mitigation (writer-strict / reader-lenient, as already run for CA-003 value resolution, version stamping, and unknown dot-prefixed members) does fit the existing asymmetry, and the memo is right not to claim it settles the matter. Of the three landing options it offers, **the third is the right one: a MUST gated to documents claiming storage-tier use**, which makes 4b conditional on Call 1 rather than universal. If Call 1 is ratified as drafted, that gate has a natural home.

### 4c — A caveat the memo did not reach: RFC 8785 is JSON-only

JCS canonicalizes JSON. **It does nothing for the archive.** A CATIO bundle's bytes include ZIP metadata — entry mtimes, compression method, entry order, extra fields — so two semantically identical bundles differ in bytes even with byte-identical JSON inside. Byte-identical round-trip for *bundles* would additionally require a canonical ZIP profile (fixed timestamps, fixed entry order, fixed compression method), and that is precisely where the memo's own warning — *"canonicalization is easy to implement subtly wrong and the failure is invisible until a diff"* — bites hardest.

Any canonicalization proposal must therefore state **whether it governs the JSON document only or the archive as well.** For thingalog's declared raw-JSON store path, JSON-only is sufficient and the ZIP question never arises — which is another reason to gate 4b to storage-tier use rather than impose it on every writer of every bundle.

## Call 5 — §3.4 system provenance: ACCEPT AS FILED, against promotion

Agreed on the reference user's own recommendation. "Provenance" in catdef today is user-authored field content (`CATDEF_SPEC.md:81`, `:1660`, plus `x.pxcatalog.com.provenance_score` at `:1425`); system lineage is absent. Provenance semantics vary sharply between runtimes, thingalog keeps its history in a separate store on volume grounds, and there is no cross-implementation demand to point at. **`x.thingalog.*` is the right instrument if MUST #7 turns out to mean system lineage**, and resolving that ambiguity is thingalog's charter work, not the spec's.

Listed here so that a later session finds it dispositioned rather than overlooked.

## Call 6 — §6's declared deviation is CONFORMANT, and the spec should say so at no cost

Thingalog declares that its **import** path will sniff and unpack (conformant) while its **store read** path will require raw JSON and refuse a `PK` prefix outright.

**That is conformant as declared.** CATIO's sniffing MUST binds **importers** — *"importers that reject outer-extension mismatches are non-conformant; content-sniffing is the authoritative discriminator."* A database read on a Worker against a 20–250 KB budget is not an importer, so the MUST does not reach it.

**Their security reasoning is sound and is endorsed rather than merely tolerated.** A store path that helpfully sniffs and unpacks an archive where it expected raw JSON is a decompression-bomb surface. *Be liberal in what you accept* is a courier's instinct and the wrong one for a storage tier.

**The cheap win, recommended for 1.5: scope the sniffing MUST to importers explicitly.** It is a clarification, not a change — no behaviour moves, no document becomes invalid, no reader breaks. It removes an ambiguity that currently makes a correct and security-motivated practice look non-conformant, and it answers the memo's open question (*does the standard want to say anything about non-importer consumers?*) with the minimum that question needs: not a new category, just a scope on the MUST already written.

This also matters beyond thingalog. Today every consumer is an importer by assumption, and that assumption is doing unstated work in the spec. If Call 1 is ratified, the assumption stops holding generally, and the scope becomes necessary rather than merely tidy.

## Call 7 — Blocker 4 is answered, and it simplifies this seat's own guidance

**Director ruling, 2026-11-25: BOTH — raw JSON and bundles, for different purposes.** This closes #46 Blocker 4.

Thingalog independently reports the same split from its own side: the live artifact published on write and served to AI peers is **raw JSON with photos by reference** (free-tier estimate 20–30 KB against a ~250 KB storage-tier threshold, so an artifact carrying photo bytes cannot be 30 KB and cannot be republished on every write), while the **bundle is an on-demand export.** Two adopters converging on the same shape, reached independently and from different constraints, is a stronger signal than either alone.

**Consequence, adopted from the memo's §7 and propagated:** this seat's `2026-11-25-1908` guidance clause — *keep the inner member named `catalog.opencatalog` until readers carry `.catx`* — **binds only bundle exports**, because a raw-JSON document has no inner member at all. The memo offered this as a possible simplification rather than asserting it, pending the ruling. The ruling has landed and the simplification is correct.

The dual-envelope-key obligation is **unaffected** and still applies to both shapes, since raw JSON carries the envelope too.

## Amendment 2026-11-25 — Director ruled STORAGE, and it changes the shape of Call 4b

**The ruling.** Call 1 as drafted: CATIO is transport and should say so in 1.5; the catdef *document* is
already a storage artifact by value #7 ("one file, complete product" — completeness is a store's property)
and value #1 (at L1 the file *is* the store, because there is no other one). **The Director ruled
storage.** Recorded 2026-11-25.

### What follows immediately

- **Thingalog needs no profile for comments or tombstones.** The two easy wins are core work, not
  adopter-local work, and their fallback assumption — proceed as transport-only and build a documented
  superset — is cancelled before it cost them anything. That timing is the whole value of their having
  filed before TAL-1596 was started.
- **Calls 2 and 3 proceed to proposal artifacts.** Tombstones carry the separate-member constraint from
  Call 2. Comments remain blocked on the policy question in Call 3, which is this seat's to draft and is
  now **more** urgent, not less — see below.
- **Call 6 moves from "cheap win" to "required."** Scoping CATIO's content-sniffing MUST to *importers*
  was recommended as a tidy clarification on the reasoning that "today every consumer is an importer by
  assumption." With storage-tier use admitted, that assumption is now definitively false: a store read
  path is a first-class consumer that is not an importer. The scope has to be stated in 1.5 or the MUST
  reaches consumers it was never written for.

### The consequence the drafting did not anticipate: Call 4b's gate collapses

Call 4b deferred the canonical byte-identical serialization MUST and said that **if** adopted, the right
landing was the filing memo's third option — *a MUST gated to documents claiming storage-tier use* — which
made it conditional on Call 1.

**That gate no longer carves anything out.** If the catdef document is a storage artifact generally, then
"documents claiming storage-tier use" is every document, and the gated MUST becomes a universal MUST on
every writer. That is precisely the tightening hazard the filing memo raised against itself in its §5: a
writer emitting valid but non-canonical JSON is conformant today and would stop being conformant, which is
not the additive shape value #5 blesses.

**So the ruling makes 4b harder rather than easier**, and this is recorded rather than allowed to drift,
because the natural reading — *storage was admitted, therefore canonicalization follows* — is wrong.

**Call 4a is unaffected and proceeds.** The round-trip losslessness test needs no canonicalization at all,
because losslessness is verifiable by semantic deep-compare. It remains the cheapest and highest-value item
in the filing.

**Call 4b stays DEFERRED, and its three remaining landings are now:**

1. **SHOULD rather than MUST**, universally. No writer becomes non-conformant; the property is stated and
   encouraged; conformance cannot test it as a gate.
2. **MUST on explicit opt-in** — a document declares canonical serialization in its envelope and is then
   held to it. Preserves testability, breaks nobody, and costs one optional field. **This seat's
   recommendation** now that the storage gate has collapsed.
3. **Remain unspecified**, and let 4a's round-trip test carry the whole burden.

None of the three is urgent, and none blocks Calls 2, 3 or 6.

### Note on Call 3, which the ruling sharpens

Admitting storage makes the comment-payload policy question more pressing rather than less. A transport
format carries third-party content briefly; a storage format **holds** it. If a catdef file is where a
relative's note on a photograph lives, then the question of who declares `.machine-translate` over that
note — the catalog author or the commenter — is a question about durable custody of someone else's words,
not about a transfer.

This also connects to what [CA-021](CA-021.md) Call 7 found the same evening: the reference renderer
ignores `.machine-translate` entirely ([#52](https://github.com/catdef/catdef-spec/issues/52)). The policy
model is about to be asked to govern third-party content in a storage artifact, and the reference
implementation does not yet honour it for first-party content in a transport one. **Call 3 should not be
drafted until #52 and #53 are fixed**, because a policy model specified against a runtime that cannot
enforce any policy is specified against nothing.
