# CA-007 Decision — Defer to v1.5 i18n-coverage triage cycle

**Disposition:** Defer formal proposal to v1.5
**Origin:** [canonical/AUTHORING_FEEDBACK.md CA-007](../canonical/AUTHORING_FEEDBACK.md) (filed 2026-04-19 by reference-implementor during PR-B, the post-v1.4 `.machine-translate: "Never"` demonstration)
**Decided:** 2026-04-19 by scott (strategist review)

## Disposition

CA-007 (Translatability of String values inside `Table` rows) is **deferred from immediate proposal-drafting to the v1.5 i18n-coverage triage cycle**. No build directive is issued. The CA-007 report in `canonical/AUTHORING_FEEDBACK.md` stays as the institutional memory; formal proposal authoring waits for the v1.5 cycle when related i18n / policy questions can be triaged together.

## Rationale

CA-007 is a real ambiguity, not a missing-enumeration nit. Reference-implementor's gap analysis correctly identifies that Table-cell translatability raises substantive design questions the i18n proposal didn't anticipate:

1. **bbox spatial linking is per-row.** If a `Table` cell's String value carries `{".en": "...", ".fr": "..."}`, does the French translation still spatially link to the same English-original photo region declared on the row's bbox? Translation may invalidate the spatial-link assumption (a French inscription transcription may differ in length / line-break behavior, breaking the bbox alignment), or the assumption may need to be re-stated as "spatial link is to the row, not to the locale-specific cell content." Either is defensible; the spec doesn't say.

2. **Per-cell vs per-row policy attachment.** If `.machine-translate: "Never"` applies to a Table row's `Text` cell, does it apply to that cell only, to the whole row, or to the whole Table? An Inscriptions Table with `Text` and `Notes` columns may want different policies per column. The spec doesn't specify the attachment scope.

3. **Column-type scoping.** Does translatability apply to all column types or only String / RichText? `Date` and `Number` cells aren't translatable in the spec's existing rule; should Table cells inherit that or expand it? Affects which Table designs surface ambiguity at all.

4. **Interaction with the existing translatable-fields enumeration.** The i18n proposal's "Which fields are translatable" list explicitly enumerates `label`, `description`, `prompt`, `title`. It implicitly extends to item-level field values (the canonical demonstrates this with item Title and Provenance). Whether that extension covers Table cells is a question of how literally to read the enumeration — and the spec should pick a side rather than leave it implicit.

These questions are not "extend the rule trivially." They are substantive design work that benefits from being designed alongside other v1.5 i18n-coverage questions, not in isolation.

## Why design alongside other v1.5 work

The v1.5 work pickup list (in strategist memory) includes two threads that overlap CA-007's design surface:

- **Field-level policies beyond i18n** (i18n proposal OQ8 follow-on): if policies extend to redistribution / attribution / retention / consent, the per-cell vs per-row attachment question for `.machine-translate` is the same shape as the per-cell vs per-row question for any policy. Designing them in isolation produces inconsistent attachment semantics; designing them together produces one rule.

- **Item-level value-shape polymorphism necessity** (v1.5 pre-question 2a): the i18n decision deferred this with the subcat-Label workaround as the v1.4 path. CA-007 raises the parallel question for Table cells. If item-level polymorphism turns out to be unnecessary for enum values (because subcat-Label covers it), Table-cell polymorphism may have an equivalent workaround — or may not, because Tables don't have a subcat-equivalent enrichment layer. This needs to be thought through with the parent question.

Triaging CA-007 in isolation would risk locking in design choices that should be made coherently with these adjacent threads. Deferring is not "kicking the can"; it's correctly scoping the design work.

## What does NOT change

- The canonical's Inscriptions Tables (items 1, 2, 8) continue to use plain String values, which is unambiguously valid under v1.4. No canonical-side change required.
- v1.4 conformance suite is unaffected.
- No spec text changes from this decision.

## v1.5 strategy work needed before CA-007 can be formally triaged

When the v1.5 i18n-coverage cycle starts, the strategist + user need to work through:

1. **Position on the four design questions in the Rationale above.** Each needs a decision before a proposal can be drafted.
2. **Coherence with field-level-policies-beyond-i18n (OQ8 follow-on).** Per-cell vs per-row attachment should be decided once and apply uniformly to all policies, not separately per policy.
3. **Coherence with item-level-polymorphism v1.5 pre-question.** If the strategist concludes item-level value polymorphism is not needed (because subcat-Label covers enum values), that conclusion should be checked against Table-cell context — Tables have no subcat-equivalent layer, so the workaround logic may not transfer.
4. **Conformance test design.** Whatever design lands needs corresponding `ft-i18n-*` or `ft-table-*` tests, similar to the gating pattern established for the v1.4 policy-compliance dimension.

Recommended sequencing: triage CA-007 alongside OQ8 follow-on as a coordinated v1.5 i18n-coverage bundle, similar to how v1.4 bundled CA-001/002/003/006/i18n.
