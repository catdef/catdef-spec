## Disposition

This decision establishes two things:

1. **The "designated reference user" pattern** as a generalization of the existing canonical-reference-file practice — a single-implementer signal source whose demand drives canonical promotion through the normal proposal-and-decision pipeline. Value #4 (extension-namespace-first) requires cross-implementer demand to be *demonstrated*; this decision formalizes that demand from a designated reference user counts as demonstration, on the same footing as demand from the canonical reference file.

2. **Thingalog as the first designated reference user** of catdef, alongside the canonical reference file (`riverside-heritage-reference-v1.4.opencatalog`). Designation effective immediately.

## Rationale

### Why the pattern needs formalizing

The strict reading of value #4 (cross-implementer = multiple unrelated conformant catdef products) is tighter than the spec's own practice. The canonical reference file has driven canonical shape across CA-001 through CA-008 as a single-implementer signal source — its demands have promoted features to v1.4 normative text. That precedent is already established; what's missing is the *general pattern* that lets other trusted single-implementer signal sources operate the same way.

Without formalization, every Thingalog-driven gap-proposal (and there will be many — primary-index, rich-Value structure, audio, future) gets re-litigated against value #4 from scratch. The strategist seat either holds the strict line (slow, frustrating, and inconsistent with canonical-file practice) or loosens it ad-hoc (inconsistent application, no institutional memory of why). Formalizing the pattern resolves both failure modes.

### What "designated reference user" means

A designated reference user is a real implementation of the spec — shipping or shipping-soon — whose gap-proposals are treated as **qualifying cross-implementer demand for purposes of value #4 promotion gating**. Specifically:

- The reference user's demand signal does NOT require a second unrelated implementer to converge on the same shape before promotion can begin
- The reference user's gap-proposals flow through the **same proposal-and-decision pipeline** as any other source — memo → strategist disposition → maintainer drafts proposal → Director ratifies → maintainer drafts conformance tests → merge. **No pipeline bypass.**
- Reference user designation does NOT create authority to amend the spec — the no-in-flight-amendment red line stands. Reference users file feedback; the spec org disposes.

### Why Thingalog qualifies as the first designation

Four criteria apply:

1. **Real implementation** — shipping (slice 11.1 activated 2026-05-24; Thingalog tenants in production)
2. **Operationally coupled to the spec org** — same Director (Scott), same human strategist-handling-handoff model, deliberate substrate-vs-consumer relationship per the OAGP family layering
3. **Pipeline-respecting** — gap-proposals arrive as memos via thingalog-strategist; this seat triages; maintainer drafts; Director ratifies. Exactly the canonical flow. The 2026-05-25T20:00 memo from thingalog-strategist is itself an exemplar of the pattern.
4. **Substrate-consumer relationship** — Thingalog consumes catdef; catdef is Thingalog's substrate. The relationship is structural, not opportunistic.

All four hold today. Designation effective immediately.

### Boundary preserved: red line still applies

The red line *"Spec amendments MUST go through the feedback channel and proposal-and-decision pipeline. No in-flight amendment from any reference implementation"* (from `org/catdef-spec-organization.opencatalog`) is **preserved unchanged**. Reference-user designation does NOT permit Thingalog (or any future designee) to amend catdef-spec mid-session-during-implementation-work. Designation changes what qualifies as promotion-driving demand — it does NOT change the pipeline or the prohibition on backdoor amendments.

## Criteria for future designations

Future strategist sessions considering additional reference-user designations should require all four of:

| Criterion | What it means |
|---|---|
| Real implementation | Shipping or imminently-shipping; not speculative |
| Operationally coupled or formally committed | Direct working relationship with the spec org, OR a memo of understanding documenting the reference-user role |
| Pipeline-respecting | History of gap-proposals flowing through normal channels; no backdoor amendments attempted |
| Substrate-consumer relationship | The implementation consumes the spec as substrate; the relationship is structural |

A single CA-NNN decision designates a new reference user, lists which of the criteria apply, and may scope the designation (e.g., "reference user for renderer concerns" vs "general reference user"). Designations are revocable by future CA-NNN if the relationship changes.
