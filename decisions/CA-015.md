# CA-015 Decision — Security handoff doctrine for elevated MCP keys

**Disposition:** Accept
**Origin:** Chat-exposure incident during the 2026-05-25 → 2026-05-26 catdef-strategist session arc; rotation executed by canonical-implementor 2026-05-26 afternoon; flagged in [memos/2026-05-26-1700--canonical-implementor--catdef-strategist--key-rotation-complete-secure-storage-posture.openthing](../memos/2026-05-26-1700--canonical-implementor--catdef-strategist--key-rotation-complete-secure-storage-posture.openthing) as strategist-consideration item #1
**Drafted:** 2026-05-26 by catdef-strategist
**Decided:** 2026-05-26 by scott (strategist review)

## Disposition

The canonical delivery channel for AI-peer MCP bearer tokens is **the MCP client config layer (`~/.claude.json` on the Director's machine)**, NOT conversation output. This decision formalizes the doctrine, retires the chat-handoff pattern, and codifies the operational shape going forward.

## What was wrong (the incident in one paragraph)

During the 2026-05-25 → 2026-05-26 session arc, the Director minted elevated MCP keys for the catdef-strategist + catdef-maintainer seats and posted them verbatim in chat. The receiving AI session used those bearers in Bash tool calls (curl `-H "Authorization: Bearer cdfk_dir_..."`). The keys therefore landed in tool input strings — captured in any persisted transcript. Public commit of the transcript would have permanently exposed both elevated keys to anyone reading the public catdef-spec repo. The exposure was caught before commit; canonical-implementor rotated both keys; old keys are revoked in D1 (production confirmed returning 401 for them); new keys live only in `~/.claude.json` + the Director's password manager + the D1 hashed-value column.

## The doctrine

**Bearer tokens live in `~/.claude.json` (MCP client config).** They never enter:
- Conversation output (the AI's text replies)
- Tool call arguments (curl Bearer headers, env-var inlines, etc.)
- Transcript files
- Git history of any repo, public or private
- Any committed artifact (memos, decisions, READMEs, prompt files)

**The flow for issuing or rotating a seat's bearer token:**

1. Director runs `node scripts/issue-api-key.mjs` locally on their machine (helper at `github.com/catdef/catdef.org`); plaintext key appears in PO terminal only
2. Director copies plaintext into password manager (recovery)
3. Director runs `claude mcp add --transport http --scope user catdef-<seat> https://catdef.org/mcp --header "Authorization: Bearer <key>"` to register the server in `~/.claude.json`
4. Director runs `wrangler d1 execute catdef-feedback --command "INSERT INTO api_keys (label, tier, hash) VALUES (...)"` (or equivalent) to register the SHA-256 hash server-side
5. **Plaintext key is NEVER copy-pasted into a Claude Code chat, terminal output that the AI sees, or anywhere the AI session might capture it**

**The flow for a session using the bearer token:**

1. Claude Code session starts; reads `~/.claude.json` at startup
2. Catdef MCP server appears in the session's tool surface as `mcp__catdef-<seat>__*` tools
3. AI session calls MCP tools natively — the runtime adds the Authorization header transparently
4. The bearer never enters the model's context

**Seat-handoff memos** referring to elevated MCP access describe the `~/.claude.json` config pattern. They do NOT describe the key value, hint at it, or recommend any flow that surfaces it.

## What changes

- The Director-side flow for minting keys formalizes as documented above (already the working pattern post-rotation)
- Seat-handoff memos use the new wording (no key values in memo bodies; no key values in commit messages; no key values in chat output that gets transcribed)
- Future strategist + maintainer sessions onboard against `~/.claude.json`-registered MCP servers and never see raw bearers

## What does NOT change

- The catdef.org/mcp server design or auth-tier model (the vulnerability was operational, not architectural)
- The Director's role as key custodian (still issues, still rotates, still revokes)
- The three-tier auth model (anonymous / standard / elevated)
- Existing local transcripts containing the revoked keys (they are dead; harmless; institutional record of the incident itself)
- The proposal-and-decision pipeline or any other governance discipline

## Rationale notes

**Why a CA-NNN and not just a memo:** the doctrine is load-bearing security infrastructure. Future strategist sessions onboard via [CLAUDE.md](../CLAUDE.md) + [`decisions/`](.) + [`memos/`](../memos/); a CA-NNN appears in `catdef_list_decisions` and is inheritable. A memo would not be (memos rotate out of active attention as new ones arrive).

**Why not amend a value-that-doesn't-move:** the values list captures spec-level commitments (L1 sacred, completeness, declarative-not-imperative, etc.); operational security doctrine is a different category. Adding to the values list would conflate spec content with operational practice.

**Why preserve existing transcripts containing the revoked keys:** the keys are dead. Redacting them now adds noise without changing the security state. They serve as institutional record of the incident — a future strategist session reading the catdef-strategist seat's history sees the chat-exposure event itself and inherits the doctrine that followed.

**Why the doctrine applies to all AI-peer MCP access, not just catdef-strategist + catdef-maintainer:** the failure mode (key plaintext in conversation → transcript → public commit) is universal. Standard-tier keys, thingalog-strategist keys, sncro keys, openbraid keys — same shape, same risk. The cross-spec coordination memo elevates this to OAGP-level codification.
