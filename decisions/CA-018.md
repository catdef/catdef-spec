## Disposition

Three calls bundled in one decision:

### Call 1 — Ratify the catalog-vs-application framing as catdef-canonical

The framing thingalog-strategist's PO ratified maps cleanly onto catdef's substrate-vs-consumer principle and is **adopted as catdef-canonical guidance** for future promotion decisions:

> *catdef canonicalizes* **data shape** *and* **generic presentation primitives** *that any catdef renderer could honor; the consumer spec or consumer application owns* **renderer-specific configurations** *that only its renderer has the concept of. The* `.x-` *namespace is the substrate's designated home for those — they stay* `.x-` *permanently. The* `.x-` *namespace is its literal purpose, not a holding pattern.*

This formalizes how value #4 (extension-namespace-first) gets applied in practice when "should this be canonical?" comes up. The cut: **is the concept renderer-portable?**

- *Yes* → canonical
- *No, renderer-specific* → permanent `.x-`

This framing is build-directive material for CLAUDE.md / CONTRIBUTING.md (Directive 3 below) and applies retrospectively: the three Thingalog `.x-` chrome vars (`.x-header_style`, `.x-card_meta_fields`, `.x-card_footer_field`) **stay `.x-` permanently** — Thingalog-application extensions, no canonical equivalent needed, no tracking-as-pending owed.

### Call 2 — Promote `.x-subtitle` to canonical `.subtitle`

`.subtitle` becomes an optional string field on the catalog root.

- **Type:** string (translatable per the v1.4 polymorphic-translatable-field pattern — accepts plain string OR object with locale keys)
- **Semantics:** catalog strapline; catalog content; surfaced wherever the renderer surfaces catalog identity
- **Inheritance:** **root-only** (not inherited by subcats); aligns with Thingalog's empirical `_NON_INHERITED_ABOUT_KEYS` precedent
- **Forward compatibility:** existing catalogs without `.subtitle` remain valid; renderers gracefully omit when absent

### Call 3 — Promote `.x-quick_filters` as items in `.views` reserved subcat

Saved Views graduate to **items in a reserved `.views` subcat**, not a flat canonical variable. Thingalog-strategist offered both shapes ("flat var OR subcat — catdef's call"); the subcat shape is the catdef-canonical answer.

- **Slot:** `.views` (reserved subcat, sibling to `.presets`)
- **Template:** `View` — fields `label` (translatable string), `filter` (opaque string per current spec; filter grammar codification deferred to its own cycle per CLAUDE.md §Known Work Items), `sort` (optional structured `{field: string, direction: "asc" | "desc"}`)
- **Inheritance:** root-only (not inherited by subcats); matches Thingalog's empirical model and the `_NON_INHERITED_ABOUT_KEYS` precedent
- **MCP parity:** falls out for free via the canonical reserved-subcat machinery
- **CRUD/sharing/permissions/versioning:** admitted by the subcat shape if/when needed, without migration

#### Why subcat over flat var

Five reasons, in order:

1. **Composes with `.presets` precedent** — operational metadata as reserved subcats is an established pattern. Promoting Saved Views to a flat array creates an inconsistency with `.presets` that future implementers would have to learn around.
2. **Native structure** — Saved Views data is `{label, filter, sort}`; a reserved-subcat-with-items expresses that structurally rather than as opaque JSON inside a string-valued variable.
3. **Future-proof for sharing/permissions/versioning** — Thingalog's flagged future needs (per-view CRUD, share-a-view URLs, view-versioning) all become incremental adds against subcat items rather than requiring a flat-var-to-subcat migration later.
4. **MCP parity for free** — `.presets` already has `catdef_list_items`-style access; `.views` inherits the same machinery without bespoke work.
5. **Operational-metadata-as-reserved-subcats doctrine** — thingalog-strategist's own cited principle. Aligning catdef-canonical with the doctrine the reference user already operates under reduces friction in their adoption.

#### Withdrawn: §2.2 Presets+Views unification

The 2130 memo flagged §2.2 (unify Presets+Views into one "preset = {filter, sort, look}"). The 2330 refinement dissolves it under the catalog-vs-application framing: Presets are Thingalog-application chrome bundles (look-only, Thingalog-internal); Views are catalog config data (portable). Different layers; not a unification candidate. **Withdrawn from catdef's queue** per the 2330 memo; this decision concurs.

#### Deferred: filter grammar codification

The `View.filter` field is opaque-string-for-now. Codifying the filter grammar is the spec's natural next deliverable per CLAUDE.md §Known Work Items, but it's substantive enough to warrant its own cycle and is not bundled with this CA-018. When the filter grammar lands, `View.filter` becomes typed against that grammar.

## Rationale notes

**Why CA-010 applies cleanly:** thingalog is the designated reference user; demand for `.subtitle` and Saved Views is grounded in real PO/Karen empirical work across multiple catalogs (welch-arctic-collection chrome work, magazine-flow catalog cards, AI-curator-as-quick-filter-author). The cross-implementer demand bar of value #4 is satisfied per CA-010 without requiring a second non-Thingalog implementer to converge. Promotion proceeds through the standard proposal-and-decision pipeline (this CA-018 → maintainer proposal drafts → Director ratification → conformance tests → spec text merge); CA-010 changes what qualifies as demand, not the pipeline.

**Why the framing call (Call 1) is worth ratifying separately:** future "should this be canonical?" decisions benefit from a sharp test rather than ad-hoc case-by-case reasoning. The catalog-vs-application framing IS that test. Ratifying it as catdef-canonical guidance — even though it doesn't change CATDEF_SPEC text directly — pre-positions future strategist sessions to make consistent calls without re-deriving the framing each time.

**Why subcat (Call 3) instead of flat var:** the operational-metadata-as-reserved-subcats pattern is already in catdef (via `.presets`). Adding `.views` as a flat array would create an inconsistency that future implementers (and the canonical surface) would have to reason about. The subcat shape costs slightly more substrate-design effort upfront and yields a far more composable, future-proof artifact.
