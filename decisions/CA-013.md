## Disposition

Three independent housekeeping calls resolved in one decision (CA-009 precedent):

### Call 1 — Legacy POST /feedback GitHub-issue auto-creation: SUNSET

The pre-existing `createGitHubIssue` behavior on the legacy `POST /feedback` HTTP endpoint **is sunset.** Going forward, all feedback submissions (legacy HTML form path AND new MCP `catdef_report_feedback` path) are **private at submission**, going public only via explicit curation (`catdef_attach_decision` with `make_public: true`, or strategist-side promotion via decision artifact citation).

### Call 2 — Deploy automation: ADD GitHub Actions workflow

The catdef.org repo gains a `.github/workflows/deploy.yml` triggering on push-to-main, deploying via `wrangler deploy` with a Cloudflare API token secret. Replaces the current manual-only deployment posture.

### Call 3 — Canonical-implementor bot identity: RATIFY `canonical-implementor@catdef.org`

The provisional `canonical-implementor <canonical-implementor@catdef.org>` identity used on the catdef-plugin initial commit and the catdef.org/mcp v0.1 commits is **ratified as the canonical seat identity for the canonical-implementor role.** Same pattern as CA-009 ratified strategist and maintainer identities.

## Rationale

### Call 1 — Why sunset, not preserve-as-feature

CA-008 established the canonical privacy posture: *"All feedback private at submission. Goes public only via curation."* That's the rule for AI-peer feedback via MCP. The legacy HTML-form behavior (auto-creating a public GitHub issue on submission) predates CA-008 and creates an asymmetry where the **submission method determines the privacy state** — which is a value #7 violation (declarative-not-imperative; the submission method is implementation, not semantics).

Of canonical-implementor's three options:

- **(i) Sunset entirely** — uniform privacy posture; submission method becomes implementation-neutral. **Chosen.**
- **(ii) Keep asymmetry as a feature** — would require documentation explaining "HTML submitters self-select public; MCP submitters get private," which exposes implementation accidents as semantic distinctions. Rejected.
- **(iii) Add `catdef_create_public_issue` MCP tool** — over-engineers what is fundamentally a curation operation. The existing `catdef_attach_decision({make_public: true})` already covers the public-promotion path. Rejected.

Existing GitHub issues from past auto-created submissions stay as historical record (no rewriting). The handler simply stops creating new ones.

### Call 2 — Why GitHub Actions, not CF dashboard integration or manual

Canonical-implementor noted PO had mentioned push-to-deploy was wired up, but the repo had no workflow file and v0.1 required manual `wrangler deploy`. Three options:

- **(i) GitHub Actions with CF API token** — deploys visible in git history, standard GitOps shape, replayable, auditable. **Chosen.**
- **(ii) Configure Cloudflare's GitHub integration in CF dashboard** — hides deploy logic outside the repo; harder to audit; CF-vendor-specific. Rejected.
- **(iii) Continue manual `wrangler deploy`** — doesn't scale beyond one implementer; manual steps get forgotten under load. Rejected.

Standard secret hygiene applies to the CF API token; it's a single secret with bounded scope (deploy-only).

### Call 3 — Why ratify and not pick a different scheme

The canonical-implementor seat now has authorship history across two repos (catdef-plugin initial commit `e641be2`; catdef.org commit `5d3e453`) under the provisional `canonical-implementor@catdef.org` identity. Continuing to mark provisional adds noise without changing behavior. CA-009 ratified strategist + maintainer with the same reasoning; this completes the three-seat ratification triangle. Form unchanged; "provisional" wording retires.
