# CA-006 Decision — Conformance validator shape coverage

**Disposition:** Accept with modifications
**Origin:** [canonical/AUTHORING_FEEDBACK.md CA-006](../canonical/AUTHORING_FEEDBACK.md) (filed 2026-04-18 by canonical-builder during validator integration; PR #24)
**Proposal:** [proposals/validator-shape-coverage.md](../proposals/validator-shape-coverage.md) (on branch `proposal-validator-shape-coverage`, PR #25)
**Decided:** 2026-04-19 by scott (strategist review)

## Build directive

catdef-maintainer to revise the proposal with the following changes before opening the PR to main:

1. **Resolve Open Questions 1, 2, and 3 in-proposal as normative text.** Brother-maintainer's own recommendations on each are correct; promote them. Move the alternatives into the Alternatives Considered section if they're substantive enough to merit memory.
    - **OQ1 (`og_image` underscore vs `og:image` colon):** Resolve as `og_image`. Cite the colon-form Open Graph property name in the key's description, but use the underscore form in JSON. Reasoning: JSON keys with colons require escaping at every consumer; convention favors snake_case for interop. The colon form is documentation, not interchange.
    - **OQ2 (URL format validation):** Implement a lightweight prefix check (`startswith("http://") or startswith("https://")`). Deeper validation (DNS, reachability, TLS) stays a runtime concern; the validator remains static.
    - **OQ3 (range/shape mismatch):** A field def without `range: true` that receives a range-shaped object MUST be rejected explicitly. The `range` attribute is load-bearing; silent acceptance hides the bug class brother-maintainer correctly identified.

2. **Confirm version stamp at 1.4 minor.** Brother-maintainer's own recommendation in OQ4 is correct: the URL object schema is new normative spec text regardless of whether the validator changes are tooling. Promote the recommendation to the proposal header; remove the patch-vs-minor question from Open Questions.

3. **Bundle-lock with the v1.4 release (overrides OQ4 sub-question).** Brother-maintainer recommended no bundle-lock on the theory that validator work doesn't change runtime behavior. The strategist disagrees on principled grounds:
    - The URL object schema formalization IS new runtime-relevant spec text introduced at v1.4
    - Per CA-002, any catdef document using the URL object form MUST stamp v1.4 (because the schema is defined at v1.4)
    - If validator-shape-coverage ships independently as 1.4.1, the URL schema lives at 1.4 but the `ft-shape-07` regression test (which validates a v1.4 document containing URL objects) lives at 1.4.1. That's the mid-version contradiction CA-002's writer-strict stamping rule was designed to prevent.
    - Bundling avoids the issue at near-zero cost; the proposal is small enough to ride along with the rest of v1.4.

    Add an explicit Release-Management section to the proposal noting bundle coordination with CA-001, CA-002, CA-003, the i18n / `primaryLocale` proposal, and the MCP conformance work.

4. **Highlight `ft-shape-07` in the proposal's Summary.** Currently the regression-test-against-canonical mechanism is buried in the Conformance Tests section. It is the most strategically important addition in the proposal: it makes "canonical and conformance suite drift apart" structurally detectable, completing the four-artifact self-correcting loop with a structural enforcer rather than an editorial discipline. Add one sentence to the Summary noting that `ft-shape-07` makes the canonical a self-checking artifact of the conformance suite.

5. **No other substantive changes.** The core design — validator extension for `Date` circa/range, `Money` range, `Number` range, and `URL` object; URL schema formalization in CATDEF_SPEC.md §Field Types; `ft-shape-01` through `ft-shape-07` — is approved as-drafted. The pseudocode is well-thought-through. The Alternatives section correctly rejects extension-namespace relegation (B) and scope-expansion to polymorphic translatable fields (C).

## Rationale

**Resolving OQs 1/2/3 in-proposal.** A pattern has now appeared across CA-001, CA-002, CA-003, and CA-006: brother-maintainer drafts an Open Question with a self-recommendation, then defers the call to the maintainer. An Open Question with a recommendation is a draft decision; it should be promoted into normative text. The strategist resolves these in advance because the recommendations are sound and the deferrals are reflexive rather than substantive. See "Pattern observation" below — this is feedback for brother-maintainer, not a one-off.

**Version stamp.** Pattern is now firmly established. Brother-maintainer is self-aware about it (OQ4 explicitly invokes "the precedent of CA-001/002/003"). Reinforce by promoting their own recommendation rather than re-litigating.

**Bundle-lock.** This is the substantive call where strategist and maintainer diverge. The reasoning above is the strategic one: any document with a URL object stamps v1.4, and shipping the validator that tests this at a different version creates exactly the mid-version drift CA-002 was designed to prevent. The "validator work is just tooling" framing misses that the URL formalization is normative spec, not just tooling.

**`ft-shape-07` highlighting.** Strategically, this is the proposal's most important addition. The four-artifact loop (spec / canonical / validator / runtime) was previously kept consistent by editorial discipline. `ft-shape-07` makes drift between canonical and validator structurally detectable: if either changes without the other, the test fails. That deserves visibility in the Summary, not burial in the test list.

## Pattern observation (for catdef-maintainer)

Brother-maintainer's proposals consistently use Open Questions as a place to propose-and-retreat. Across four proposals reviewed, every Open Question with a self-recommendation has been resolved by strategist triage in favor of the recommendation. Going forward:

- **Promote** an Open Question to normative proposal text when you have a recommendation you'd defend on review.
- **Reserve** Open Questions for genuine trade-offs without a clear winner, or for governance decisions outside the maintainer role's scope (e.g., MIME registration, bot-identity ratification).

This is not a criticism of the proposals — they have all been excellent — but a process refinement that reduces strategist-loop overhead and makes the proposals stand more confidently on their own.
