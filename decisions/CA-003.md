# CA-003 Decision — Subcat value resolution

**Disposition:** Accept with modifications
**Origin:** [canonical/AUTHORING_FEEDBACK.md CA-003](../canonical/AUTHORING_FEEDBACK.md)
**Proposal:** [proposals/subcat-value-resolution.md](../proposals/subcat-value-resolution.md) (on branch `proposal-subcat-value-resolution`)
**Decided:** 2026-04-18 by scott (strategist review)

## Build directive

catdef-maintainer to revise the proposal with the following changes before opening the PR to main:

1. **Change version stamp from patch to minor.**
    Current: `Target version: 1.3.1 (patch — clarifies ambiguous prose; the watches sample and the canonical currently exhibit the redundancy)`.
    Revise to: `Target version: 1.4 (minor — introduces a new importer MUST, a new validation class, and a change to the required resolution order for Enumerated namespaces)`.
    This aligns with CA-001 and CA-002; the three proposals set the pattern that new normative obligations are minor-level, regardless of how small the prose change looks.

2. **Soften the SHOULD-omit rule to MAY-omit.**
    In the proposed §Value resolution text, change:
    > A writer SHOULD omit `data.values.<target>` when `subcats.<target>.values` is declared, to avoid redundancy.

    to:
    > A writer MAY omit `data.values.<target>` when `subcats.<target>.values` is declared; the `subcats.<target>.values` keys are the authoritative namespace. A writer MAY also include `data.values.<target>` as a subset — this is useful when the catdef is targeted at L1 runtimes that ignore subcats and benefit from a pre-declared namespace.

    Rationale: the core disambiguation rule (subcats-authoritative-when-both-present) stands without normative pressure toward omission. Writers optimizing for L1-renderer ergonomics may legitimately want both forms present.

    **Related: drop the canonical-simplification follow-on.** The proposal's Requested Maintainer Actions bullet 5 mentions "a small PR drops the redundant `data.values.<name>` entries from `canonical/catalog.opencatalog`." Remove this bullet. The canonical stays as-is (carrying both forms) to serve as a reference for the L1-friendly authoring pattern.

3. **Adopt asymmetric strictness for the superset case (mirror CA-002).**
    The proposal's Open Question 2 identifies writer-strict / reader-lenient as the right answer and backs off "for simplicity." Reinstate it. Revise the proposed §Value resolution text for the superset case:

    > **Superset validation (mirror of forward-compat asymmetry).**
    >
    > A writer MUST NOT emit a catdef in which `data.values.<target>` contains names that are not keys of `subcats.<target>.values`. Writer-side validation tools MUST reject such documents.
    >
    > A reader encountering such a document MUST NOT reject it on this basis. The reader MAY warn that `data.values.<target>` contains names not seeded in `subcats.<target>.values`. The reader resolves the value namespace from `subcats.<target>.values` only; extra names in `data.values.<target>` are ignored.
    >
    > This asymmetry — writer strict, reader lenient — matches the pattern established by the `catdef` version-stamping rule.

    Update conformance test `ft-subcat-values-04`:
    - Rename to `ft-subcat-values-04a` (writer side): A writer-side validator MUST reject `invalid_data_values_superset.opencatalog`.
    - Add `ft-subcat-values-04b` (reader side): A reader MUST parse and render `invalid_data_values_superset.opencatalog` without refusal; it MAY emit a warning; the resolved namespace is the `subcats.<target>.values` keys only.

4. **Promote Open Question 1 into normative text.**
    The L1 item-inference behavior belongs in CATDEF_SPEC.md §Conformance Levels §Level 1, not an open question. Add to the proposed change section:

    > ### Amend CATDEF_SPEC.md §Conformance Levels §Level 1
    >
    > Append a paragraph clarifying the L1 runtime's Enumerated-namespace resolution:
    >
    > > An L1 runtime that ignores subcats MUST be able to resolve an Enumerated field's value namespace from item references at render time when `data.values.<target>` is not present. The pre-declared namespace (from `subcats.<target>.values` or `data.values.<target>`) is an optimization; the item-reference fallback is the L1-mandatory path. This guarantees that a catdef using subcat-only Enumerated namespaces remains L1-renderable without requiring the L1 runtime to implement subcat resolution.

    Remove Open Question 1 from the proposal once this text is added.

5. **Drop `ft-subcat-values-06` (round-trip normalization).**
    Mandating that exporters strip redundant `data.values` entries on round-trip adds implementation cost without enabling any behavior the disambiguation rule needs. It also prevents legitimate "preserve input byte-for-byte" importer implementations, which are useful for diff-and-review workflows on catdef files.
    Remove the test. Remove Open Question 4 from the proposal (since the recommendation it contains is being rejected).

6. **Resolve Open Question 3 (shared namespaces) with affirmative prose.**
    Add to the proposed §Value resolution text:

    > **Shared namespaces.** A subcat's value namespace is shared across all templates, fields, and subcats that reference it by target name. Multiple references resolve to the same value set; there is no per-reference scoping.

    Remove Open Question 3.

7. **No other substantive changes.** The core design is approved as-drafted:
    - `subcats.<target>.values` authoritative when present
    - `data.values.<target>` authoritative when no subcat
    - `subcats.<target>` with `field_defs` but no `values`, paired with `data.values.<target>`, remains the empty-seed pattern for future enrichment
    - The decision tree for writers (enriched vs bare-name vs empty-seed) is clear and stays
    - Test fixtures `valid_subcat_values_only`, `valid_subcat_plus_matching_data_values`, `valid_data_values_only`, `valid_empty_subcat_plus_data_values` retained as-drafted

8. **Release-management constraint.** Merge-to-main held until the v1.4 bundle is coherent: CA-001, CA-002, CA-003, the i18n / `primaryLocale` proposal, and the MCP conformance work land together. Branch advance is fine.

## Rationale

**Version stamp.** Third consecutive proposal where a "small-looking" prose change carries new normative weight. Establishing 1.4 minor as the consistent answer for this class of change is now more important than litigating each case individually. Patch-level framing will keep drifting back in without a named precedent.

**MAY-omit instead of SHOULD-omit.** The L1-runtime argument the proposal's Alternative D raises is correct, and the proposal's own resolution (item-inference) handles the rendering case — but pre-declared namespaces are a real L1 affordance for UI ("here are all possible values"). Forcing writers toward the omission pattern removes that affordance silently. A MAY rule keeps the core disambiguation (subcats authoritative) while letting writers optimize for their target runtime. The canonical staying as-is — with both forms present — reinforces this by example.

**Asymmetric strictness.** CA-002 established strict-writer / lenient-reader as the spec's pattern for new normative rules. CA-003 is the first test of whether that pattern generalizes beyond version stamping. It does, and should, because the reasons are the same: writers control what they emit and can be held to a hard rule; readers encounter arbitrary files in the wild and should be robust. Simplifying to "validation error at import" (which the maintainer proposed and then backed off from) leaves ambiguity about which side enforces, and loses the consistency benefit.

**L1 item-inference as normative.** The proposal currently leaves L1 behavior for subcat-only Enumerated fields as an open question. That's a gap — conformant L1 runtimes need a defined answer, and divergent implementations (some fail, some infer, some render blanks) will cause user-visible breakage. Promoting the inference rule into normative L1 text closes the gap and aligns with value #1 (L1 is sacred) by ensuring subcat-only catdefs remain L1-renderable.

**Drop round-trip normalization.** The SHOULD in `ft-subcat-values-06` imposes writer work for an aesthetic benefit (simpler re-exports) without behavioral need. Importers that re-export byte-for-byte are legitimate — they support diff workflows, audit trails, and format-preservation tooling. The disambiguation rule doesn't care about normalization; mandating it is scope creep.

**Shared namespaces.** The canonical already depends on multi-reference subcats working as expected. Affirming this in prose closes the open question and prevents future sessions from re-litigating it.
