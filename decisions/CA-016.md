# CA-016 Decision — Reference renderer source placement at catdef-spec/renderer/

**Disposition:** Accept
**Origin:** PO directive 2026-05-26 evening (during catdef-strategist post-rotation session arc); motivated by `github.com/catdef/catdef.org` repo being set private + the resulting listing-copy staleness flagged pre-submission of the catdef plugin to the claude-community marketplace
**Drafted:** 2026-05-26 by catdef-strategist
**Decided:** 2026-05-26 by scott (strategist review)

## Disposition

The reference L1 renderer's source lives at **`catdef-spec/renderer/`** — a new sibling directory to `conformance/`, `canonical/`, `decisions/`, etc. The repo `github.com/catdef/catdef.org` continues to host the deployed instance at `render.catdef.org` but pulls (or vendors) the renderer source from `catdef-spec/renderer/`. `catdef.org/` repo stays private; spec + reference renderer stay public in `catdef-spec/`.

## Rationale

### Parallel construction with existing canonical-reference patterns

`catdef-spec/conformance/` carries the reference test suite (the suite IS the standard, per value #5). `catdef-spec/canonical/` carries the canonical reference catalog (`riverside-heritage-reference-v1.4.opencatalog` — the worked example that drives v1.4 normative shape). Adding `catdef-spec/renderer/` as a sibling reference artifact is structurally consistent: each is a publicly-readable canonical implementation of a normative spec aspect, located alongside the spec text itself.

The v1_success_criterion in [org/catdef-spec-organization.opencatalog](../org/catdef-spec-organization.opencatalog) already names "an operational L1 reference renderer at render.catdef.org" as part of v1 success. Until now the renderer source has lived in a separate repo (`catdef.org/`); placing it in `catdef-spec/renderer/` makes the artifact genuinely referenceable at the canonical spec location.

### Why this preserves the open-source-renderer claim in the listing copy

The plugin's marketplace listing pitched the reference renderer as **"live at render.catdef.org … with open source at github.com/catdef/catdef.org for self-hosting or embedding."** (The catdef-spec README itself does not carry this bullet; only the plugin README and the plugin packaging brief in `catdef-spec/memos/` do — the brief is internal record of what was authored at packaging time.) When the canonical-implementor's work in CA-008/CA-013 expanded `catdef.org/` to also contain hosting infrastructure (Cloudflare Workers source, deploy config, secret-handling helpers), the Director (correctly per CA-015's spirit) set that repo to private. The open-source-renderer claim in the plugin listing immediately went stale — clicking the link from the marketplace would have hit a 404 or auth wall.

Three options were considered:

- **(A) Drop the open-source-renderer framing entirely.** Loses the self-hosting / embedding value-add from the marketplace pitch.
- **(B) Split the renderer source into a separate public repo (e.g., `github.com/catdef/catdef-render`).** Clean but invents a new repo for a small artifact; adds repo-management overhead.
- **(C) Revert catdef.org to public.** Reverses the privacy decision; exposes hosting/deploy/secret-handling details.
- **(D) Move the renderer source into `catdef-spec/`.** PO's proposal. Preserves both the open-source claim AND catdef.org's privacy; aligns with parallel-construction-of-reference-artifacts pattern.

Option (D) chosen. Cleanest answer; lowest operational surface; reinforces the existing public/private separation.

### Reinforcement of CA-015's separation-of-hosting-from-spec doctrine

CA-015 codified that elevated MCP keys live in `~/.claude.json`, not in conversation output — operational doctrine separating "key material handling" from "everything else." This decision applies the same separation principle to repo content: hosting/deploy/operational-secret details belong in the private `catdef.org/` repo; spec content + canonical reference artifacts (including the reference renderer) belong in the public `catdef-spec/` repo. Same logic, different layer.

## Build directives

### Directive 1 — canonical-implementor (next session in that seat)

Execute the renderer source move:

1. **Extract** the renderer source from `github.com/catdef/catdef.org` (the L1 browser-only HTML/CSS/JS bundle; SSRF-guarded `/fetch` proxy if it's renderer-specific; static assets). Do NOT move: MCP server source (`src/mcp/*`), deploy config (`.github/workflows/deploy.yml`, `DEPLOYING.md`, `wrangler.toml` if private), secret-handling helpers (`scripts/issue-api-key.mjs`, `scripts/register-mcp-key.mjs`), D1 migrations, `src/index.ts` routing.
2. **Place** extracted source at `catdef-spec/renderer/` per this decision. Include a `renderer/README.md` describing what's there (L1 reference renderer for catdef artifacts), how to self-host or embed, and the relationship to the hosted instance at render.catdef.org.
3. **Update** the `catdef.org/` deploy mechanism to read renderer source from `catdef-spec/renderer/` — either via git submodule, periodic vendor-snapshot, or build-time fetch. Implementer's choice; trade-offs are tactical.
4. **Drop** the now-redundant renderer source location in `catdef.org/`. Preserve git history for institutional record (no rewrite); just remove the active source.
5. **Status memo back** to catdef-strategist when complete, including: the deploy-pull mechanism chosen, any deltas from the strategist intent, and live verification that render.catdef.org still serves correctly.

### Directive 2 — catdef-maintainer (no urgency; bundle with next governance text update)

Future governance-text updates may acknowledge `catdef-spec/renderer/` as a sibling reference artifact alongside `conformance/` and `canonical/`. Specifically: README's "What's in this repo" table gains a `renderer/` row; CONTRIBUTING.md may need a small note about the renderer source if proposals touch it; CLAUDE.md's session-startup procedure may benefit from listing `renderer/` as one of the dirs to scan when proposals touch L1 conformance.

None of this blocks the renderer move or the plugin submission.

- `catdef.org/` deploy pipeline reads renderer source from `catdef-spec/` (post-implementor-execution)
- The internal plugin packaging brief at `catdef-spec/memos/2026-05-25-1900--...body.md` retains the original (now-stale) listing-copy text as point-in-time institutional record; not rewritten

## What does NOT change

- `github.com/catdef/catdef.org` repo's private status (preserved per Director's call; reinforced by this decision's logic)
- `render.catdef.org` URL or runtime behavior (hosted instance continues unchanged from the user's perspective)
- catdef-spec governance, decisions, proposals, or any value
- L1 conformance level definition (renderer source moving doesn't change what L1 means; just where the reference implementation source lives)
- Existing renderer source in `catdef.org/` git history (preserved as institutional record; no rewrite)

## Rationale notes

**Why a CA-NNN and not just a build directive in a memo:** the placement decision is substrate-architecture — where in the canonical artifact set the reference renderer lives. Future strategist sessions onboarding via CLAUDE.md + decisions/ inherit the call legibly. A memo would not surface in `catdef_list_decisions` and would rotate out of active attention.

**Why "renderer/" and not "reference-renderer/" or "render/":** parallel construction with `conformance/` (also a single-word reference-artifact directory). PO confirmed `renderer/`.

**Why move now and not as part of v1.5:** the listing-copy staleness is current — the marketplace submission is imminent and the previous link target is private. Fixing this requires either listing-copy retreat or a public source location; placement decisions don't wait on minor-version cycles. The actual code move is implementer execution and proceeds on the canonical-implementor seat's clock; the strategist call (placement) lands now.
