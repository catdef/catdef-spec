# CA-021 Decision — Latent capability asserted but unexercised: three instances in three weeks, one defect class, one standing remedy

**Disposition:** Accept the pattern as a named defect class. Adopt the **exercise requirement** below as standing practice. **PENDING Director ratification** — it imposes an obligation on every seat, which is a governance change.
**Origin:** Raised by `canonical-implementor` 2026-11-16 on discovering that `catdef.org`'s deploy pipeline had not run since 2026-05-26, proposing it "seems worth a decision of its own rather than another entry in someone's notes." Routed to this seat. Third instance of a pattern whose first two were recorded piecemeal in [CA-019](CA-019.md) Call 4.4 and [CA-020](CA-020.md) Q2.
**Drafted:** 2026-11-16 by catdef-strategist
**Conformance level affected:** None — this is a governance practice, not spec text.

## The pattern

Three failures in three weeks, in three unrelated artifact types, all with the same shape:

| # | Artifact | What was asserted | What was true | Found by |
|---|---|---|---|---|
| 1 | Conformance suite | 174 tests green proves the renderer conformant | Tests ran against a **Python stand-in**; nothing exercised the shipped JS. CA-017 survived **174 days** behind a green suite | `canonical-implementor`, reading the harness |
| 2 | Installed-base measurement | 1,064 `.openthing` files | **~700 distinct**; `tl-179` is a clone of `thingalog`, double-counted by 52% | This seat, after `canonical-implementor` flagged it was single-sourced |
| 3 | Deploy pipeline | `catdef.org` pushes reach production with no staging step (CA-013 Call 2's premise) | `CLOUDFLARE_API_TOKEN` invalid. **No successful deploy since 2026-05-26 — 174 days.** Pushes fail | `canonical-implementor`, on the first push in 174 days |

**The common defect: a capability was asserted, relied upon, and never exercised in a way that could fail.**

Each was green-looking. None was verified. In all three the appearance of working was *produced by the absence of exercise* rather than merely coexisting with it — a suite that never touches the renderer cannot report the renderer broken, a count nobody audits cannot report its own double-counting, and a pipeline nobody runs cannot report a dead credential.

Two of the three had been true, undetected, for the **same 174 days**, both dating from the CA-016 session — the last work to touch production, which left two invisible breakages behind it. That coincidence is not causal but it is instructive: **the interval over which a capability goes unexercised is the interval over which it can be silently broken**, and nothing in the system was measuring that interval.

## Why this needs a decision rather than three notes

Each instance was individually recorded and individually remedied. That is the failure mode. Three notes in three artifacts produce no cross-cutting practice, and the next instance — in a fourth artifact type nobody has thought of yet — gets discovered the same way: by accident, by someone choosing to actually run the thing.

This is the same **structural-beats-procedural** argument CA-019 Call 2 made against relying on everyone remembering that one directory is production. A pattern held in three separate notes is procedural knowledge. Named as a class with a standing obligation, it is structural.

## Call 1 — The exercise requirement

**Before a capability is relied upon in a decision, an authorization, or a claim, it must be exercised in a way that could have failed.**

Concretely, by capability type:

1. **A test or guard** — must be demonstrated capable of going red. Already standing practice per CA-019 Call 4.4 (negative controls), promoted here from a renderer-specific expectation to a general one. A guard not shown to fail is not a guard.

2. **A deploy or publish pipeline** — must have a **confirmed successful run** before any authorization is requested or granted that depends on it. A gated-act authorization request must state when the pipeline last succeeded. Where a pipeline is idle for long periods, the idleness itself is the risk: see Call 2.

3. **A measurement** — must state its method and be reproducible by another seat from that statement. A bare figure is an assertion. The specific trap: counting without interrogating what the buckets contain, which is exactly how instance 2 happened.

4. **A credential or access grant** — must be verified against the system it authorizes by **exercising it**, not inferred from any property of its record. **A secret that exists is not a secret that works.**

   **Worked example, and it is sharper than the rule as first drafted.** Instance 3's token was **not expired**: its window ran 2026-05-25 → 2027-05-31, with six months left. Two timestamps settle what happened — the GitHub secret was last written `2026-05-26T16:38:35Z`, and the first successful deploy ran `16:39:11Z`, 36 seconds later as a `workflow_dispatch`. That is the Director following `DEPLOYING.md`'s rotation procedure and confirming with a manual run. So the stored secret held its original May value, untouched, while the token on Cloudflare's side was active, in-window and correctly scoped — **and still rejected it.** Rolling is the only operation that produces exactly that state: a new value issued, the entry otherwise unchanged. The Director rolled it and reset the secret; it deployed first try.

   The instructive part: **every signal available from the dashboard said the credential was healthy. Name, status, scopes, expiry — all green, all true, and all irrelevant** to whether the stored value still authenticated. **An expiry check would have passed and told us nothing.** So "verified against the system it authorizes" must mean *the value*, not *the entry* — a distinction that looks pedantic until it costs 174 days. This generalizes past credentials: wherever a record and the thing it describes can drift, checking the record is not checking the thing.

5. **A record** — must not be read as evidence of the live state of the thing it describes. Established separately in the binding-residence line of findings (a session binding answers which session, never whether it lives; a ref reissue and a session death are indistinguishable in the record) and consistent with this class.

**The test to apply:** *if this capability were broken right now, what would tell me?* If the answer is "nothing, until someone needs it," it is unexercised and this requirement applies.

## Call 2 — Consequence for CA-013 Call 2 and CA-019 Call 1: the gate was ceremonial, and the wrong surface was guarded

Recorded because it is uncomfortable and load-bearing.

**CA-013 Call 2** gates `catdef.org` pushes *on the premise that they reach production with no staging step*. For some unknown portion of the last 174 days that premise has been **unsatisfied**: pushes to `catdef.org` main do not reach production, they fail. The gate has been guarding a door that does not open.

Meanwhile **CA-019 Call 1** extended the gate to `catdef-spec/renderer/**` on `main` — and that surface *does* still deploy, because the live Worker's `main` pin is currently **the only working deploy path this project has.** So Call 1 was not merely prudent; it was, unknowingly, the only part of the gate that was guarding anything real.

**Neither gate is withdrawn.** CA-013 Call 2's premise is temporarily unsatisfied, not wrong — it becomes true again the moment the token is valid, and a gate that is correct in principle should not be relaxed because its subject is briefly broken. The finding is not "the gate was unnecessary." It is:

> **An unexercised gate and an unexercised pipeline are the same defect, and the gate cannot detect it.** Authorization ceremony around a broken mechanism produces confidence without protection — arguably worse than no gate, because the ceremony is itself evidence that someone is paying attention.

**Remedy, per Call 1.2:** an authorization request for a gated act states when the pipeline last succeeded. Had that been required on 2026-11-16, "last successful deploy: 2026-05-26, 174 days ago" would have appeared in the request, and the token would have been checked before the act rather than discovered by it.

## Call 3 — Credit where the method was the point

All three instances were found the same way: **a seat chose to exercise something rather than trust its appearance.** None was found by review, by reading, or by a passing suite.

- Instance 1: reading the harness to ask *what does this test actually touch?*
- Instance 2: a seat flagging that a load-bearing number it had not verified **was not verified**, declining to let the record imply two confirmations where there was one — which prompted the audit that found the error.
- Instance 3: a preflight that passed, followed by reading the deploy result instead of reporting the non-regression hash that would have shown success.

Instance 3 deserves emphasis because the trap was armed and documented in advance. CA-019 recorded that the post-step-2 hash check *cannot distinguish success from failure*, since a no-op deploy produces identical bytes either way. Production did serve `b4a512fa…` afterward, the check did pass, and it passed **because nothing deployed.** Reported on that basis, a failed deploy would have been reported as a success.

**The practice that caught all three is cheap and the failures it catches are not.** That asymmetry is the argument for Call 1.
