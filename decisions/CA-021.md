# CA-021 Decision — Latent capability asserted but unexercised: three instances in three weeks, one defect class, one standing remedy

**Disposition:** Accept the pattern as a named defect class. Adopt the **exercise requirement** below as standing practice. **PENDING Director ratification** — it imposes an obligation on every seat, which is a governance change.
**Origin:** Raised by `canonical-implementor` 2026-11-16 on discovering that `catdef.org`'s deploy pipeline had not run since 2026-05-26, proposing it "seems worth a decision of its own rather than another entry in someone's notes." Routed to this seat. Third instance of a pattern whose first two were recorded piecemeal in [CA-019](CA-019.md) Call 4.4 and [CA-020](CA-020.md) Q2.
**Drafted:** 2026-11-16 by catdef-strategist
**Conformance level affected:** None — this is a governance practice, not spec text.

## The pattern

Three failures in three weeks, in three unrelated artifact types, all with the same shape:

| # | Artifact | What was asserted | What was true | Found by |
|---|---|---|---|---|
| 1 | Conformance suite | 174 tests green proves the renderer conformant | Tests ran against a **Python stand-in**; nothing exercised the shipped JS. CA-017 survived **174 days** behind a green suite | `canonical-implementor`, reading the harness |
| 2 | Installed-base measurement | 1,064 `.openthing` files | **~700 distinct**; `tl-179` is a clone of `thingalog`, double-counted by 52% | This seat, after `canonical-implementor` flagged it was single-sourced |
| 3 | Deploy pipeline | `catdef.org` pushes reach production with no staging step (CA-013 Call 2's premise) | `CLOUDFLARE_API_TOKEN` invalid. **No successful deploy since 2026-05-26 — 174 days.** Pushes fail | `canonical-implementor`, on the first push in 174 days |
| 4 | Branch protection on `catdef-spec` `main` | `CONTRIBUTING.md`: merges happen "only by human maintainers through the normal pull-request review process"; the bot identity "does not have merge authority on protected branches" | A `pull_request` rule **does** exist — and the step-3 push **bypassed it**, because the only available credential is the Director's account, which holds bypass. `remote: Bypassed rule violations for refs/heads/main` | `canonical-implementor`, on the first direct push to a protected branch |

**The common defect: a capability was asserted, relied upon, and never exercised in a way that could fail.**

Each was green-looking. None was verified. In all three the appearance of working was *produced by the absence of exercise* rather than merely coexisting with it — a suite that never touches the renderer cannot report the renderer broken, a count nobody audits cannot report its own double-counting, and a pipeline nobody runs cannot report a dead credential.

Two of the three had been true, undetected, for the **same 174 days**, both dating from the CA-016 session — the last work to touch production, which left two invisible breakages behind it. That coincidence is not causal but it is instructive: **the interval over which a capability goes unexercised is the interval over which it can be silently broken**, and nothing in the system was measuring that interval.

## Why this needs a decision rather than three notes

Each instance was individually recorded and individually remedied. That is the failure mode. Three notes in three artifacts produce no cross-cutting practice, and the next instance — in a fourth artifact type nobody has thought of yet — gets discovered the same way: by accident, by someone choosing to actually run the thing.

This is the same **structural-beats-procedural** argument CA-019 Call 2 made against relying on everyone remembering that one directory is production. A pattern held in three separate notes is procedural knowledge. Named as a class with a standing obligation, it is structural.

## Call 1 — The exercise requirement

**Before a capability is relied upon in a decision, an authorization, or a claim, it must be exercised in a way that could have failed.**

Concretely, by capability type:

1. **A test or guard** — must be demonstrated capable of going red. Already standing practice per CA-019 Call 4.4 (negative controls), promoted here from a renderer-specific expectation to a general one. A guard not shown to fail is not a guard.

2. **A deploy or publish pipeline** — must have a **confirmed successful run** before any authorization is requested or granted that depends on it. A gated-act authorization request must state when the pipeline last succeeded. Where a pipeline is idle for long periods, the idleness itself is the risk: see Call 2.

3. **A measurement** — must state its method and be reproducible by another seat from that statement. A bare figure is an assertion. The specific trap: counting without interrogating what the buckets contain, which is exactly how instance 2 happened.

4. **A credential or access grant** — must be verified against the system it authorizes by **exercising it**, not inferred from any property of its record. **A secret that exists is not a secret that works.**

   **Worked example, and it is sharper than the rule as first drafted.** Instance 3's token was **not expired**: its window ran 2026-05-25 → 2027-05-31, with six months left. Two timestamps settle what happened — the GitHub secret was last written `2026-05-26T16:38:35Z`, and the first successful deploy ran `16:39:11Z`, 36 seconds later as a `workflow_dispatch`. That is the Director following `DEPLOYING.md`'s rotation procedure and confirming with a manual run. So the stored secret held its original May value, untouched, while the token on Cloudflare's side was active, in-window and correctly scoped — **and still rejected it.** Rolling is the only operation that produces exactly that state: a new value issued, the entry otherwise unchanged. The Director rolled it and reset the secret; it deployed first try.

   The instructive part: **every signal available from the dashboard said the credential was healthy. Name, status, scopes, expiry — all green, all true, and all irrelevant** to whether the stored value still authenticated. **An expiry check would have passed and told us nothing.** So "verified against the system it authorizes" must mean *the value*, not *the entry* — a distinction that looks pedantic until it costs 174 days. This generalizes past credentials: wherever a record and the thing it describes can drift, checking the record is not checking the thing.

5. **A record** — must not be read as evidence of the live state of the thing it describes. Established separately in the binding-residence line of findings (a session binding answers which session, never whether it lives; a ref reissue and a session death are indistinguishable in the record) and consistent with this class.

**The test to apply:** *if this capability were broken right now, what would tell me?* If the answer is "nothing, until someone needs it," it is unexercised and this requirement applies.

## Call 2 — Consequence for CA-013 Call 2 and CA-019 Call 1: the gate was ceremonial, and the wrong surface was guarded

Recorded because it is uncomfortable and load-bearing.

**CA-013 Call 2** gates `catdef.org` pushes *on the premise that they reach production with no staging step*. For some unknown portion of the last 174 days that premise has been **unsatisfied**: pushes to `catdef.org` main do not reach production, they fail. The gate has been guarding a door that does not open.

Meanwhile **CA-019 Call 1** extended the gate to `catdef-spec/renderer/**` on `main` — and that surface *does* still deploy, because the live Worker's `main` pin is currently **the only working deploy path this project has.** So Call 1 was not merely prudent; it was, unknowingly, the only part of the gate that was guarding anything real.

**Neither gate is withdrawn.** CA-013 Call 2's premise is temporarily unsatisfied, not wrong — it becomes true again the moment the token is valid, and a gate that is correct in principle should not be relaxed because its subject is briefly broken. The finding is not "the gate was unnecessary." It is:

> **An unexercised gate and an unexercised pipeline are the same defect, and the gate cannot detect it.** Authorization ceremony around a broken mechanism produces confidence without protection — arguably worse than no gate, because the ceremony is itself evidence that someone is paying attention.

**Remedy, per Call 1.2:** an authorization request for a gated act states when the pipeline last succeeded. Had that been required on 2026-11-16, "last successful deploy: 2026-05-26, 174 days ago" would have appeared in the request, and the token would have been checked before the act rather than discovered by it.

## Call 3 — Credit where the method was the point

All three instances were found the same way: **a seat chose to exercise something rather than trust its appearance.** None was found by review, by reading, or by a passing suite.

- Instance 1: reading the harness to ask *what does this test actually touch?*
- Instance 2: a seat flagging that a load-bearing number it had not verified **was not verified**, declining to let the record imply two confirmations where there was one — which prompted the audit that found the error.
- Instance 3: a preflight that passed, followed by reading the deploy result instead of reporting the non-regression hash that would have shown success.

Instance 3 deserves emphasis because the trap was armed and documented in advance. CA-019 recorded that the post-step-2 hash check *cannot distinguish success from failure*, since a no-op deploy produces identical bytes either way. Production did serve `b4a512fa…` afterward, the check did pass, and it passed **because nothing deployed.** Reported on that basis, a failed deploy would have been reported as a success.

**The practice that caught all three is cheap and the failures it catches are not.** That asymmetry is the argument for Call 1.

## Call 4 — Instance 4 is the same class pointed at governance, and it needs a Director choice this seat will not make for them

Instance 4 arrived after this decision was drafted, which is itself the argument for having drafted it: the class predicted a fourth case and the fourth case appeared inside the hour, in an artifact type nobody had been looking at.

The implementing seat's read is adopted: **a protection rule nobody exercises until it is bypassed is a rule whose effectiveness was never tested, and documentation asserting a review process that does not run is the same shape as a suite asserting coverage it does not have.** Verified at this seat: `catdef-spec` `main` carries `pull_request`, `deletion` and `non_fast_forward` rules, and the step-3 push went through the first one because the only credential available is the Director's account.

**That is not an unauthorized landing** — the act was authorized first-hand and executed exactly as described. It is a repo declaring a process it does not follow.

**Note the causal chain, because it matters for the remedy:** the bypass is a *consequence* of the attribution gap (readiness report §2.1, blocker 3), not an independent choice. There is no separate bot credential, so a seat acting at all acts as the Director, and the Director holds bypass. Fixing the documentation without fixing attribution leaves the same collapse in place, just honestly described.

**The choice is the Director's**, since it is governance. Three readings, and this seat declines to pick for them while stating a recommendation:

1. **The rule is right; future landings go through PRs.** Costs one PR per landing. Gains an actual reviewable diff — which is what the reviewability concern wanted, and it recurred once already: step 3 landed 22 files and seven charter versions in two commits.
2. **The rule is vestigial; `CONTRIBUTING.md` should stop claiming it.** Cheapest, and the most honest if direct-push-on-authorization is the real model — in which the Director's per-act authorization *is* the review.
3. **The rule binds contributors and the Director's bypass is the intended escape hatch** — in which case the exception must be documented rather than left implicit.

**Recommendation: (1), with (2) as the honest fallback.** What is not acceptable is the status quo, which is (3) *undocumented* — a claimed review process, an active rule, a routine bypass, and nothing in the repo saying so. That combination is precisely what this decision names: ceremony producing confidence without protection. A PR per landing also separates *authorizing* from *reviewing*, which currently collapse into one act, and separation of decision from execution is the organizing principle of this whole charter.

**Whichever is chosen, `CONTRIBUTING.md` must match reality.** That is the non-negotiable part and it does not depend on which reading wins.

## Call 5 — The class applies to verification procedures, not just capabilities. Two instances, both from this seat's own instructions.

Instances 1–4 are capabilities asserted without exercise. Step 4 produced two cases where **the instrument itself was unexercised** — and both originated in instructions this seat wrote.

### Instance 5 — a check that could have failed for reasons unrelated to what it tested (false negative)

This seat instructed: *"wait past the 300s TTL and report the first post-TTL sample."* **That instruction was wrong.**

`raw.githubusercontent.com` has its **own ~5-minute cache**, independent of the Worker's 300s edge TTL. **Two cache layers stack.** The implementing seat checked the deploy ref immediately after advancing `release` and found raw still serving `b4a512fa…` from a ref already pointing at `faa4433`.

A single 330s wait would have sampled inside the gap, returned the old bytes, and — **by the stop-and-report protocol this seat specified** — been reported as *the promotion did not take*. A false failure, followed by a correct escalation based on it.

It was caught by staging the check instead: poll until raw actually flips (280s), *then* wait the Worker TTL, *then* sample (320s later).

**The asymmetry is the finding.** This arc spent an entire evening guarding against **false positives** — the non-regression check that passes because nothing deployed, the suite green against a stand-in, the number nobody audits. It never once asked whether a check could fail for a reason unrelated to its subject. **A false negative is as much a broken instrument as a false positive**, and it is arguably worse here: a false positive ships something unverified, while a false negative halts correct work and sends a seat chasing a defect that does not exist. The implementing seat noted the asymmetry was its to catch and that it nearly did not; it was equally this seat's, since this seat wrote the defective instruction.

### Instance 6 — a stale cached error masking the current one

Testing whether the front-page CTA had recovered, the first sample returned **`504 "Upstream timeout (>10000ms)"` in 0.13 seconds.** A timeout that returns in 130ms is not a timeout. Three consecutive samples returned the same thing, which *looked* like consistency and was one cached object served three times.

Cache-busted with a dummy parameter to force fresh Worker execution: **`502 {"error": "Upstream body is not valid UTF-8"}`** — the error CA-019 Call 3 documented. Independently reproduced at this seat, cache-busted: **502 in 1.84s**, with controls passing (plain-JSON upstream via `/fetch` → 200; the bundle direct from GitHub → 200, 1,680,109 bytes in 0.06s). The latency gap between the cached 0.13s 504 and the live 1.84s 502 is itself the tell.

Responses carry `Cache-Control: public, max-age=30` and **error responses are cached too**, so a *historical* failure gets replayed over the current one. Reporting the 504 would have claimed the failure mode had changed and sent `catdef.org#8` chasing a timeout that does not exist.

**Remedy for both, added to Call 1:** a verification procedure is itself a capability under this decision. Before trusting a check, ask **what else could make this check report what it reports** — and for any check crossing a cached boundary, enumerate the cache layers and either bust them or confirm each has turned over. Repeated identical samples are not corroboration when a cache can serve them; this is the same error as one seat sampling twice in 20 seconds and calling it "several TTL windows later," which that seat corrected itself.

## Call 6 — The class reaches the governance record itself, and this instance shaped a Director review

Instances 1–4 are capabilities asserted without exercise. Call 5's instances 5–6 are verification
instruments that were themselves unexercised. Instance 7 is the same defect one level up: **a record and
the thing it describes drifted, and a review read the record.**

### Instance 7 — the 2026-11-25 review directed work that had been live for nine days

The full-review handoff (`memos/2026-11-25-full-review-handoff.md` §4) and the triage comment posted to
`catdef-spec#45` both direct: *"catdef.org #8 first (byte passthrough), then the client sniff-and-unpack in
#45."*

**The client sniff-and-unpack shipped 2026-11-16 and was in production when that was written.** Verified
independently at both the implementing and strategist seats: `render.catdef.org` serves 36,329 bytes at
`35e53d14`, carrying `build 001` and `CATIO-LOADER-BEGIN`, matching `release` `faa4433` byte-for-byte.

The cause is clean, and `#45`'s own comment timeline is the whole proof:

```
2026-11-01T13:25Z   strategist brief
2026-11-01T14:49Z   strategist brief (proxy half cross-reference)
2026-11-25T21:32Z   triage ruling — directs the client half as future work
```

**Nothing between.** The entire 2026-11-16 arc — CA-017's client half, CA-019's four gated steps, the
deploy, and both falsifiable tests — never reached the tracker. The review was conducted from the tracker.
It read a record that had not been updated and produced a directive that was correct in form, correct about
what to do next, and wrong about why.

This is the generalization in Call 5 pointed at a new artifact type: **wherever a record and the thing it
describes can drift, checking the record is not checking the thing.** Here the record is a GitHub issue and
the thing is a deployed renderer. The difference from instances 1–6 is consequence: this one reached the
Director's own review and shaped a work handoff to two seats.

### Why it happened, stated against this seat rather than structurally

The implementing seat's read is that this is *"a closed loop with no one inside it"* — issue comments are
outside `canonical-implementor`'s `authority_bound`, that bound exists because of the attribution gap
(#46 Blocker 3, now #48), so the seat that did the work is the one seat that cannot record it.

**That is true of them and it is generous to this seat, which had the access.** Issue-comment capability on
`catdef-spec` was tested and exercised by this seat on 2026-11-01 — comment 6559523305 on #45 and the
creation of `catdef.org#8`. On 2026-11-16 this seat wrote a 48-line step-4 completion record and put it in
`decisions/CA-019.md`, **and left that file uncommitted** pending the branch-protection question in Call 4.
Nothing was posted to #45.

So both channels to the next reader were closed by this seat's own choices, in opposite ways:

| Channel | State on 2026-11-25 | Why |
|---|---|---|
| `decisions/CA-019.md` | complete, detailed, **uncommitted** | held pending the Call 4 process question |
| `catdef-spec#45` | stale since 2026-11-01 | never updated |

The work was recorded in the one place the reviewer could not read and omitted from the one place they did
read. **That is not a structural gap, it is this seat's sequencing error**, and the structural gap the
implementing seat names sits underneath it rather than excusing it.

The compounding lesson is specific and worth more than the apology: **holding an artifact to await a process
decision is not neutral.** It looks like caution and it functions as suppression, because the artifact's
whole purpose is to inform the next reader and the next reader arrives on their own schedule. Call 4 asked
whether landings should go through PRs. Waiting for that answer cost nine days of record currency and
produced a misdirected handoff. The correct move was to land the record and raise the process question
separately — they were never actually coupled.

### Remedy, added to Call 1

- **A completion is not recorded until it is recorded where the next reader will look.** For work tracked on
  GitHub, that is the tracker, not only the repo. The two are different audiences and the repo is invisible
  to anyone reviewing from the issue list.
- **Never hold a completed record pending an unrelated process decision.** Land the record; raise the
  question on its own.
- **Where a seat cannot post to the tracker, the seat that can owes it.** With `canonical-implementor`
  unable to comment on issues until #48 lands, posting completion records for that seat's work is this
  seat's obligation, not a courtesy. #48 is the fix; until it lands this is the mitigation.
